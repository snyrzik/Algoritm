## Проект 3. `CollectionLab` — осознанная работа с STL

**Цель:** научиться применять `std::vector`, `std::list`, `std::deque` не только для хранения, но и для безопасных операций с итераторами, выбирать алгоритмы и обосновывать сложность.

Этот проект **намеренно использует STL** — это центральная тема второй половины четвёртой лекции. Не переносить запрет STL из первой лабораторной работы на эту независимую учебную задачу.

В `collection_operations.hpp` должны быть объявлены и определены следующие функции (все в `namespace collection_lab`):

```cpp
#include <cstddef>
#include <deque>
#include <list>
#include <vector>

namespace collection_lab {

void insert_marker_before_each_even(std::vector<int>& values, int marker);
void remove_negative(std::list<int>& values);
void rotate_left(std::deque<int>& values, std::size_t steps);
std::list<int> merge_sorted(std::list<int> first, std::list<int> second);

} // namespace collection_lab
```

### Обязательные контракты

**Операция 1 — `vector`:** вставить `marker` непосредственно перед **каждым исходным чётным элементом**, не обрабатывать добавленные маркеры как новые исходные элементы. Например, `{1,2,4,5}` и `marker=8` → `{1,8,2,8,4,5}`. Проверь отрицательные чётные числа и ноль. Нельзя хранить недействительные итераторы при вставке и реаллокации.

**Операция 2 — `list`:** удалить все строго отрицательные элементы; нули и положительные оставить в исходном порядке. В этой конкретной задаче использовать итераторный обход с корректным применением `erase`, чтобы закрепить правила инвалидирования; не заменять реализацию одним вызовом `remove_if`.

**Операция 3 — `deque`:** циклически сдвинуть элементы влево на `steps` позиций. Например, `{10,20,30,40}` и `steps=6` → `{30,40,10,20}`. Пустой дек не должен приводить к делению на ноль. Использовать операции на концах, не создавать вручную отдельную структуру данных.

**Операция 4 — `list`:** слить **два уже отсортированных по возрастанию списка** в новый отсортированный список, сохранив все дубликаты. Аргументы передаются по значению, поэтому исходные списки вызывающего кода не изменяются. Разрешено использовать `list::merge`. Не нужно дополнительно сортировать входные списки: это предусловие.

### Этапы

1. Спроектировать поведение и выбрать методы контейнеров.
2. Написать четыре функции самостоятельно.
3. Проверить пустые контейнеры, дубликаты, отрицательные значения, `steps > size()`.
4. Объяснить корректность итераторов.
5. Для каждой операции дать **оценку временной сложности и её обоснование**; если существуют разные корректные алгоритмы, оценка должна соответствовать собственному решению.

### Аналитическая часть проекта

Обязательные вопросы без готовых ответов на экране:

1. Почему вставка нескольких элементов в середину `vector` может потребовать квадратичного времени в наивной реализации?
2. Почему `std::list` не имеет `operator[]`?
3. Когда `std::list::splice` предпочтительнее последовательного копирования значений?
4. В чём разница `reserve` и `resize`?
5. Что значит «амортизированное `O(1)`» для `vector::push_back`?
6. Что произойдёт с сохранённым итератором на удалённый элемент списка?
7. Почему для `deque` нельзя предполагать сплошное расположение всех элементов?
