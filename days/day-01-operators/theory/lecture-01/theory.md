## Чему ты научишься за этот день

В C++ собственный класс — не просто контейнер с полями. Это тип данных со своими правилами создания, копирования, изменения и взаимодействия с другими объектами. В этой лекции мы последовательно соберём эту картину: от первых методов и ссылок до операторов `+`, `+=`, `[]`, `()` и потокового ввода-вывода.

Важнее всего **научиться выбирать корректную сигнатуру**. Например, почему `operator+=` обычно возвращает `T&`, почему `operator+` чаще возвращает `T`, почему `operator[]` иногда возвращает `T&`, а иногда `const T&`, и почему `operator<<` принимает поток по ссылке. Когда поймёшь причины, запоминать отдельные объявления станет заметно легче.

Учебные примеры используют небольшие отдельные классы: `Temperature`, `Distance`, `TripleRegister`, `OwnedInts` и `Interval`. Они показывают механизм, **но не являются готовыми решениями** самостоятельных проектов `Matrix2x2`, `CMyString` и `DynamicVector`.

# Глава 1. Класс как тип: конструкторы, ссылки, `const` и копирование

## 1.1. Что именно создаётся при объявлении класса

Начнём не с перегрузки операторов, а с вопроса: **что должно уметь значение пользовательского типа?** Число `int` можно создать, передать в функцию, прочитать, изменить и скопировать. У объекта собственного класса тоже должны быть понятные правила для этих действий.

```cpp
class Temperature {
private:
    double m_celsius;

public:
    explicit Temperature(double celsius)
        : m_celsius(celsius) {
    }

    double celsius() const {
        return m_celsius;
    }

    void increase(double delta) {
        m_celsius += delta;
    }
};
```

`class Temperature` объявляет новый **тип**. Объявление `Temperature room(21.5);` создаёт один объект этого типа, а не переменную `double`. Внутри объекта находится поле `m_celsius`, имеющее тип `double`.

`private` означает, что внешний код не обращается к полю напрямую: `room.m_celsius` будет ошибкой компиляции. Мы заранее определяем **публичный интерфейс**, через который разрешено работать с объектом.

`public` не означает «любое изменение допустимо». Это список операций, предусмотренных автором класса. Позже при реализации матриц, строк и векторов мы будем проектировать именно такой контракт.

### Конструктор и список инициализации

```cpp
explicit Temperature(double celsius)
    : m_celsius(celsius) {
}
```

Разберём эту запись:

- `Temperature` — имя конструктора совпадает с именем класса; возвращаемого типа у конструктора нет, даже `void`.
- `(double celsius)` — параметр, значение которого передаёт вызывающий код.
- `: m_celsius(celsius)` — **список инициализации членов**. Здесь поле получает начальное значение при создании объекта.
- `{}` — тело конструктора; оно может быть пустым, потому что работа уже сделана в списке инициализации.
- `explicit` запрещает некоторые неявные преобразования из `double` в `Temperature`. Это полезно, когда мы не хотим случайно смешать физическую температуру и обычное число.

Сравни два варианта:

```cpp
// Вариант A: инициализация поля
Temperature(double value) : m_celsius(value) {}

// Вариант B: присваивание внутри тела
Temperature(double value) {
    m_celsius = value;
}
```

В данном случае с простым полем `double` результат похож. Но это **не одинаковые действия**: в A поле инициализируется, в B поле уже существует, и ему присваивают значение. Для `const`-полей, ссылочных членов и некоторых пользовательских типов выбор становится принципиальным. В учебной практике предпочитай список инициализации.

### А где конструктор по умолчанию?

После объявления конструктора `Temperature(double)` запись `Temperature t;` не скомпилируется: подходящего конструктора без аргументов нет. Можно явно добавить:

```cpp
Temperature() : m_celsius(0.0) {}
```

Или выбрать одну конструкцию с аргументом по умолчанию:

```cpp
explicit Temperature(double celsius = 0.0)
    : m_celsius(celsius) {}
```

Оба варианта можно использовать, но не стоит бездумно объявлять одновременно несколько конструкторов с одинаково подходящими наборами аргументов: это может привести к неоднозначности вызова.

## 1.2. Что находится в памяти: объект, значение и адрес

Предположим:

```cpp
Temperature a(18.0);
Temperature b(27.0);
```

Логическая схема памяти:

```text
a : Temperature                 b : Temperature
┌─────────────────────┐        ┌─────────────────────┐
│ m_celsius = 18.0    │        │ m_celsius = 27.0    │
└─────────────────────┘        └─────────────────────┘
   отдельный объект                отдельный объект
```

У этих объектов независимые поля. Если вызвать `a.increase(5)`, изменение `a` не должно неожиданно затронуть `b`.

### Передача по значению: функция работает с копией

```cpp
void heat_copy(Temperature t) {
    t.increase(10.0);
}
```

При вызове `heat_copy(a)` в параметре `t` создаётся **отдельный объект**, скопированный из `a`. Когда `t` изменится, `a` останется прежним.

```text
До вызова:    a = 18.0
В функции:    t = копия a = 18.0
После heat:   t = 28.0
После выхода: a = 18.0
```

Такой способ иногда нужен специально: функция может выполнять вычисления над своей копией. Но передача больших классов по значению может вызывать лишнее копирование.

### Передача по ссылке: работа с исходным объектом

```cpp
void heat_original(Temperature& t) {
    t.increase(10.0);
}
```

Символ `&` в объявлении `Temperature& t` означает **ссылку на `Temperature`**. Вызов `heat_original(a)` позволяет функции обращаться к исходному `a`. Теперь результат `a.celsius()` действительно изменится.

Не путай две записи:

```cpp
Temperature& ref = a;   // ref — другое имя для существующего a
Temperature* ptr = &a;  // ptr — отдельная переменная-указатель с адресом a
```

Через ссылку обращаются как к объекту: `ref.increase(1)`. Через указатель: `ptr->increase(1)` или `(*ptr).increase(1)`. Для указателя допустимо значение `nullptr`, для обычной ссылки — нет аналогичного корректного «пустого» состояния.

Синтаксис зависит от контекста: в `Temperature& ref` символ `&` объявляет ссылку, а в `&a` — оператор получения адреса.

### `const T&`: читаем исходный объект и обещаем его не менять

```cpp
double read_celsius(const Temperature& t) {
    return t.celsius();
}
```

Здесь `const Temperature&` объединяет два свойства:

1. Объект не копируется при передаче аргумента.
2. Через этот параметр нельзя вызывать неконстантные методы, меняющие объект.

Поэтому `const T&` часто подходит для операций, которые **только читают** пользовательский объект: сравнение, сложение двух аргументов, вывод на экран.

Для маленького типа `int` или `double` передача по значению обычно проще и не хуже по производительности. Не нужно автоматически заменять `double x` на `const double& x`.

## 1.3. Почему `const` после метода стоит в другом месте

Вот две функции:

```cpp
double celsius() const;
void increase(double delta);
```

`const` после круглых скобок применяется не к возвращаемому значению, а к **объекту, на котором вызван метод**. Внутри `celsius() const` нельзя обычным образом изменять `m_celsius`.

```cpp
const Temperature freezing(0.0);

double value = freezing.celsius(); // Разрешено
// freezing.increase(5.0);         // Ошибка компиляции
```

Компилятор должен различать методы, разрешённые для обычного объекта, и методы, разрешённые для `const`-объекта. Отсюда важное практическое правило: **если метод не должен менять наблюдаемое состояние объекта, проверь, можно ли объявить его `const`.**

Не путай три разные записи:

```cpp
const Temperature& get_a() const;
Temperature& get_b();
Temperature get_c() const;
```

- `const Temperature&` перед именем `get_a` — тип результата: ссылка, через которую нельзя изменять возвращённый объект.
- `Temperature&` перед `get_b` — изменяемая ссылка на существующий объект.
- `Temperature` перед `get_c` — новый объект/значение, возвращаемое по значению.
- Последнее `const` после `()` в `get_a` и `get_c` — обещание, что сам вызываемый объект не будет изменён этим методом.

Тип результата и константность вызываемого объекта — **два независимых вопроса**.

## 1.4. `this` и `return *this`

Внутри нестатического метода компилятор предоставляет указатель `this` на объект, для которого метод вызван.

```cpp
void increase(double delta) {
    this->m_celsius += delta;
}
```

`this->m_celsius` и просто `m_celsius` в этом контексте обозначают одно и то же поле. Явная запись полезна, когда нужно показать, что мы обращаемся именно к члену объекта.

Если метод должен вернуть **сам изменённый объект**, часто пишут:

```cpp
Temperature& add_in_place(double delta) {
    m_celsius += delta;
    return *this;
}
```

`this` имеет тип указателя на объект (`Temperature*` в обычном неконстантном методе), а `*this` означает сам объект. Возвращаемый тип `Temperature&` требует ссылки, поэтому `return *this` здесь естественен.

```cpp
Temperature room(20);
room.add_in_place(2).add_in_place(3);
// Теперь room.celsius() == 25
```

Это важный шаблон синтаксиса, который встретится в `operator+=` и `operator=`.

## 1.5. Возвращение по значению и по ссылке: где возникает опасность

Допустим, тебе нужен метод, который выдаёт текущее число градусов.

```cpp
double celsius() const {
    return m_celsius;
}
```

Возврат `double` по значению совершенно уместен: вызывающий получает число и не может через него случайно изменить внутреннее поле.

А вот следующий код некорректен:

```cpp
// ОШИБКА: не используй такой код
const double& broken() const {
    double local = m_celsius;
    return local;
}
```

`local` — локальная переменная. После выхода из метода её время жизни закончилось; ссылка на неё становится висячей. Попытка прочитать её — неопределённое поведение.

Ссылка на поле объекта, напротив, может быть корректной, пока жив сам объект:

```cpp
const double& celsius_ref() const {
    return m_celsius;
}
```

Но даже эта ссылка станет недействительной после уничтожения объекта `Temperature`. Для простого числа полезнее возвращать `double` по значению.

**Правило:** сначала определи, должен ли вызывающий получить *копию значения* или *доступ к существующему объекту*. Только после этого выбирай `T`, `T&` или `const T&`.

## 1.6. Копирование и присваивание — разные операции

В C++ эти записи означают разные действия:

```cpp
Temperature a(10.0);

Temperature b = a;  // Создание b посредством копирования
Temperature c(a);   // Тоже создание c посредством копирования

c = a;              // Присваивание уже существующему c
```

Первая пара относится к **конструктору копирования**. Последняя строка — к **копирующему оператору присваивания**.

В маленьком классе, где все поля имеют тип `double`, автоматически создаваемые компилятором операции копирования обычно корректны: копируются сами числа.

Однако для класса, который **владеет выделенной динамической памятью**, стандартное копирование указателя может быть опасным: два объекта начнут считать один буфер своим. Это мы подробно разберём на Дне 2 при реализации `CMyString`.

### Полная программа главы

```cpp
#include <iostream>

class Temperature {
private:
    double m_celsius;

public:
    explicit Temperature(double celsius = 0.0)
        : m_celsius(celsius) {}

    double celsius() const {
        return m_celsius;
    }

    Temperature& increase(double delta) {
        m_celsius += delta;
        return *this;
    }
};

void change_copy(Temperature value) {
    value.increase(10.0);
}

void change_original(Temperature& value) {
    value.increase(10.0);
}

double inspect(const Temperature& value) {
    return value.celsius();
}

int main() {
    Temperature room(20.0);

    change_copy(room);
    std::cout << inspect(room) << '\n'; // 20

    change_original(room);
    std::cout << inspect(room) << '\n'; // 30

    room.increase(2).increase(3);
    std::cout << room.celsius() << '\n'; // 35

    Temperature copy = room;
    copy.increase(5);

    std::cout << room.celsius() << '\n'; // 35
    std::cout << copy.celsius() << '\n'; // 40
}
```

Обрати внимание на первую функцию: она действительно изменяет `value`, но **не изменяет `room`**. Именно эта разница между копией и ссылкой лежит в основе многих ошибок при реализации собственных операторов.

# Глава 2. Перегрузка операторов: от синтаксиса до корректного интерфейса

## 2.1. Почему обычному классу недостаточно методов `add` и `subtract`

Допустим, у нас есть тип `Distance`, представляющий расстояние в метрах. Без перегрузки операторов пришлось бы писать:

```cpp
Distance total = first.add(second);
```

Но сложение расстояний — понятная математическая операция. Поэтому хотелось бы получить:

```cpp
Distance total = first + second;
```

**Перегрузка оператора** связывает привычную запись с функцией, реализованной для пользовательского типа. Она **не** добавляет к языку новый символ и не позволяет менять общую грамматику выражений. Компилятор по-прежнему понимает `+` как оператор сложения, но теперь знает, какую функцию вызвать для `Distance`.

Это основная идея слайдов 2–5 первой лекции.

## 2.2. Общий синтаксис: метод и свободная функция

Оператор можно определить как **метод класса**:

```cpp
class Distance {
public:
    Distance operator+(const Distance& other) const;
};
```

Или как **свободную функцию**:

```cpp
Distance operator+(const Distance& left,
                   const Distance& right);
```

Почему количество параметров разное?

Для выражения `a + b` есть два операнда. Если оператор является методом `a`, сам левый операнд передаётся неявно через `this`. В списке параметров нужно написать только правый — `b`.

```text
Запись выражения:      a + b
Метод класса:         a.operator+(b)
Свободная функция:    operator+(a, b)
```

Для унарного `-a` ситуация аналогична: у метода нет явных параметров, а у свободной функции есть один аргумент.

| Операция | Метод класса | Свободная функция |
|---|---|---|
| `-a` | `T operator-() const` | `T operator-(const T& a)` |
| `a + b` | `T operator+(const T& b) const` | `T operator+(const T& a, const T& b)` |
| `a += b` | `T& operator+=(const T& b)` | Возможна свободная форма, но обычно метод |
| `a[i]` | `T& operator[](std::size_t i)` | В C++17 перегружается только как метод |
| `a(x)` | `T operator()(...) const` | Перегружается только как метод |

Для C++17 `operator=`, `operator[]`, `operator()` и `operator->` должны быть нестатическими методами класса. Операторы `::`, `.`, `.*`, `?:`, `sizeof`, `typeid` и некоторые другие не перегружаются. Перегрузка не меняет число операндов, приоритет и ассоциативность операторов.

Особенно важно: нельзя перегрузить оператор **только для двух встроенных типов**. Хотя бы один операнд должен быть объектом класса или перечислением подходящего типа. Нельзя написать собственное сложение двух обычных `int`, заменяющее встроенное.

## 2.3. Возвращаемый тип определяется смыслом операции

Для бинарного сложения мы ожидаем **новый результат**, а не изменение `a` или `b`:

```cpp
Distance operator+(const Distance& other) const;
```

Здесь:

- `Distance` перед `operator` означает возврат результата **по значению**.
- `const Distance& other` не допускает изменения правого операнда и не требует копировать его только ради передачи.
- `const` после `()` не позволяет изменять левый операнд через данный метод.

Совсем другой смысл у `a += b`. Этот оператор меняет сам `a`:

```cpp
Distance& operator+=(const Distance& other);
```

Возвращение `Distance&` разрешает цепочные операции и не создаёт лишнюю копию уже существующего объекта.

```cpp
Distance a(10);
Distance b(3);
Distance c(2);

a += b;
(a += b) += c;
```

Вторая цепочка в скобках работает на одном объекте `a`. Если бы `operator+=` возвращал **копию** `Distance`, последняя часть могла бы изменить временный объект вместо исходного.

### Почему часто удобно реализовать `+` через `+=`

Вместо двух почти одинаковых алгоритмов можно определить один изменяющий оператор и использовать его при создании нового результата:

```cpp
class Distance {
private:
    double m_meters;

public:
    explicit Distance(double meters = 0.0)
        : m_meters(meters) {}

    double meters() const {
        return m_meters;
    }

    Distance& operator+=(const Distance& other) {
        m_meters += other.m_meters;
        return *this;
    }

    friend Distance operator+(Distance left,
                              const Distance& right) {
        left += right;
        return left;
    }
};
```

Почему слева `Distance left` передан **по значению**? Здесь это осознанно: `left` — копия первого операнда, и мы хотим изменять **её**, сохранив оригинал. Далее `left += right` использует уже работающую реализацию. Наконец `return left` возвращает вычисленный результат по значению.

Это не единственный правильный дизайн `operator+`, но он хорошо демонстрирует связь между операторами. Такой принцип повторного использования методов отдельно подчёркивается и требованиями лабораторной.

### Полная проверка

```cpp
#include <iostream>

class Distance {
private:
    double m_meters;

public:
    explicit Distance(double meters = 0.0)
        : m_meters(meters) {}

    double meters() const { return m_meters; }

    Distance& operator+=(const Distance& other) {
        m_meters += other.m_meters;
        return *this;
    }

    friend Distance operator+(Distance left,
                              const Distance& right) {
        left += right;
        return left;
    }
};

int main() {
    Distance a(2.5);
    Distance b(7.0);
    Distance c = a + b;

    std::cout << c.meters() << '\n'; // 9.5
    std::cout << a.meters() << '\n'; // 2.5: a не изменился

    a += b;
    std::cout << a.meters() << '\n'; // 9.5
}
```

Сравни два последних действия: `a + b` создаёт новый результат; `a += b` изменяет имеющийся объект.

## 2.4. Зачем нужна свободная функция при умножении на число

В задании на вектор обычно должно работать и `vector * 2`, и `2 * vector`.

Если реализовать только метод:

```cpp
Distance operator*(double factor) const;
```

то он подходит для `distance * 2`, поскольку слева находится `Distance`. Но выражение `2 * distance` не может вызвать метод у числа `2` — ведь тип `int` не имеет нашего метода.

Нужна дополнительная свободная функция:

```cpp
Distance operator*(double factor, const Distance& distance) {
    return distance * factor;
}
```

Здесь мы используем уже готовую операцию `distance * factor`, а не копируем вычисления во вторую функцию.

Запомни не конкретный код, а ход рассуждения: **какой тип слева, кому принадлежит метод и нужен ли доступ к закрытым полям?**

### `friend` — не новый способ наследования

Если написать внутри класса:

```cpp
friend Distance operator+(Distance left, const Distance& right);
```

то `friend` разрешает этой свободной функции доступ к закрытым членам класса. Сама функция при этом **не становится методом**.

Дружба не нужна автоматически для каждого оператора. Если свободная функция может обойтись публичными методами, её вполне можно определить без `friend`. Но для `operator<<` доступ к полям через `friend` иногда удобен.

## 2.5. Унарные операции и отличие от бинарных

Для класса с одним числом унарный минус меняет знак математического значения:

```cpp
Distance operator-() const {
    return Distance(-m_meters);
}
```

Скобки у `operator-()` пусты, потому что левый операнд — сам объект, вызвавший метод.

```cpp
Distance a(4.0);
Distance b = -a;
// b хранит -4; a по-прежнему хранит 4
```

Не путай:

```cpp
-a        // Унарный оператор
 a - b    // Бинарный оператор
```

Оба обозначаются словом `operator-`, но сигнатуры различаются по числу параметров и контексту.

## 2.6. Префиксный и постфиксный `++` — почему есть фиктивный `int`

Посмотри на разницу:

```cpp
++counter;  // Сначала увеличение, затем использование результата
counter++;  // Сначала старое значение как результат выражения, затем увеличение
```

Для пользовательского типа нужно различать две сигнатуры:

```cpp
Counter& operator++();    // Префиксный
Counter operator++(int);  // Постфиксный
```

Параметр `int` в постфиксной форме — **фиктивный признак синтаксиса**, а не количество прибавляемых единиц. При обычной записи `counter++` ты не передаёшь этот аргумент вручную.

### Полный пример

```cpp
#include <iostream>

class Counter {
private:
    int m_value;

public:
    explicit Counter(int value = 0) : m_value(value) {}

    int value() const { return m_value; }

    Counter& operator++() {
        ++m_value;
        return *this;
    }

    Counter operator++(int) {
        Counter before = *this;
        ++(*this);
        return before;
    }
};

int main() {
    Counter counter(5);

    Counter a = ++counter; // counter = 6, a = 6
    Counter b = counter++; // b = 6, counter = 7

    std::cout << a.value() << ' '
              << b.value() << ' '
              << counter.value() << '\n';
}
```

Результат:

```text
6 6 7
```

Разбери внимательно `Counter before = *this;`: здесь создаётся копия **старого состояния**. Затем `++(*this)` вызывает префиксную реализацию, а `return before` отдаёт значение до изменения.

В отличие от префиксной версии, постфиксная обычно вынуждена создавать старую копию, поэтому для тяжёлых объектов может быть дороже.

## 2.7. Сравнение `==` и `!=`: особенность `double`

Сравнение целых значений обычно прямолинейно:

```cpp
return m_value == other.m_value;
```

А вот вещественные вычисления могут давать небольшую ошибку округления. Требования лабораторной прямо предусматривают **сравнение вещественных значений с заданной точностью**.

Для конечных чисел простой подход может выглядеть так:

```cpp
#include <cmath>

bool almost_equal(double a, double b) {
    constexpr double epsilon = 1e-9;
    return std::fabs(a - b) <= epsilon;
}
```

Это **абсолютная** погрешность: числа считаются близкими, когда разность по модулю не больше `epsilon`.

Обязательно понимай ограничения:

- Для очень больших и очень маленьких масштабов одной абсолютной погрешности может быть недостаточно.
- `NaN` не должен считаться обычным числом; сравнения с ним особые.
- Бесконечности также требуют отдельного внимания.
- «Равенство с погрешностью» в общем случае **не транзитивно**: из близости A к B и B к C не обязательно следует близость A к C.

Поэтому для учебного класса нужно явно определить контракт сравнения и тестировать его. Не следует без объяснений обещать, что `fabs(a-b) < epsilon` универсально корректно для всех `double`.

Часто `operator!=` реализуют через уже написанное равенство:

```cpp
bool operator!=(const Distance& other) const {
    return !(*this == other);
}
```

Здесь `*this` — текущий объект, `==` вызывает его оператор сравнения, а `!` отрицает результат. Реализация избавляет от риска, что `==` и `!=` будут использовать разные правила.

## 2.8. Какие перегрузки действительно требуются в лабораторной

Первая лабораторная работа сложнее демонстрационных примеров: её класс должен **сам управлять выделенным ресурсом**, корректно копироваться, поддерживать `==`/`!=`, потоковый вывод, исключения и типобезопасную реализацию через шаблоны там, где этого требует вариант. В частности, варианты включают векторы произвольной размерности, матрицы произвольного размера и многочлены произвольной степени.

Это **ориентир по требовательности**, а не повод немедленно превратить учебный `Distance` или `Vector3` первого дня в большую шаблонную реализацию. Владение ресурсами и шаблоны будут подробно разобраны на следующих днях. Сегодня твоя задача — безошибочно овладеть синтаксисом операторов и смыслом каждой сигнатуры.

## Закрепление после главы 2 · Класс `Duration`

> **Формат:** одна составная задача на 15–25 минут. Решение не публиковать до попытки.

Создай класс `Duration`, хранящий продолжительность в целых секундах. Отрицательные значения разрешены.

Нужно самостоятельно определить и реализовать:

1. Конструктор и константный метод чтения секунд.
2. `+=`, который изменяет левый объект и поддерживает цепочки вызовов.
3. `+`, который создаёт новый результат и не изменяет исходные объекты. По возможности повторно используй `+=`.
4. Унарный `-`.
5. `==` и `!=` с единым правилом сравнения.
6. Префиксный и постфиксный `++`, каждый увеличивает продолжительность на одну секунду, но отличается возвращаемым результатом.

Проверочные сценарии:

- `Duration a(59), b(61);` — сумма должна представлять 120 секунд, а `a` и `b` оставаться прежними.
- Для отдельного объекта со значением 7 сначала вызови префиксный `++`, затем постфиксный, сохрани результаты обоих выражений и объясни отличие.
- Убедись, что выражение `(a += b) += Duration(3)` изменяет именно `a`.
- Проверь арифметику с отрицательной продолжительностью и неизменяемость `const`-операндов.

**Критерии:** осмысленный выбор «метод или свободная функция»; корректное количество параметров; `const`; возврат `Duration` и `Duration&`; отсутствие лишних побочных эффектов; правильная семантика префиксного и постфиксного оператора; переиспользование уже работающей операции.

# Глава 3. `operator[]`, `operator()`, ссылки на элементы и границы

## 3.1. Зачем объекту собственная индексация

Массив имеет привычный синтаксис:

```cpp
int numbers[3] = {10, 20, 30};
int value = numbers[1];  // 20
numbers[1] = 50;
```

Если пользовательский класс хранит несколько значений, хочется работать с ним похожим образом:

```cpp
object[1] = 50;
```

Для этого существует `operator[]`.

В C++17 этот оператор перегружается как **нестатический метод класса**. Слева от скобок — объект, на котором вызывается метод, справа — один передаваемый аргумент индексации. Сам аргумент не обязан быть `int`: в лекции приводится пример словаря, индексируемого ключом типа `const char*`. Однако для числового массива естественно использовать целочисленный индекс.

## 3.2. Почему `operator[]` часто возвращает ссылку

Посмотри на класс с тремя регистрами:

```cpp
#include <cstddef>
#include <stdexcept>

class TripleRegister {
private:
    int m_data[3];

public:
    TripleRegister(int first, int second, int third)
        : m_data{first, second, third} {}

    int& operator[](std::size_t index) {
        if (index >= 3) {
            throw std::out_of_range("Invalid register index");
        }

        return m_data[index];
    }

    const int& operator[](std::size_t index) const {
        if (index >= 3) {
            throw std::out_of_range("Invalid register index");
        }

        return m_data[index];
    }
};
```

Тут впервые вместе появляется несколько связанных конструкций.

### Неконстантная версия

```cpp
int& operator[](std::size_t index)
```

Она возвращает **ссылку на существующий элемент массива**, поэтому результат можно использовать слева от присваивания:

```cpp
TripleRegister r(10, 20, 30);
r[1] = 99;
```

Концептуально происходит следующее:

```text
До:    m_data = [10, 20, 30]
                  │
                  └── r[1] возвращает ссылку на этот элемент

r[1] = 99;

После: m_data = [10, 99, 30]
```

А если метод возвращал бы просто `int`?

```cpp
int operator[](std::size_t index);
```

Тогда он отдавал бы **числовое значение по копии**. Чтение `int x = r[1];` возможно, но стандартная запись изменения `r[1] = 99` не работала бы: результат не является изменяемой ссылкой на элемент.

### Константная версия

```cpp
const int& operator[](std::size_t index) const
```

Здесь сразу два `const`, и они отвечают на два разных вопроса:

- `const int&` — вызывающий не получает через результат право изменять элемент.
- `const` после `()` — этот метод разрешено вызывать у константного объекта.

```cpp
const TripleRegister fixed(1, 2, 3);
int number = fixed[1];       // Можно читать
// fixed[1] = 100;           // Нельзя менять
```

Нельзя просто оставить одну изменяемую версию, если хочешь поддерживать доступ к `const TripleRegister`. С другой стороны, если оставить только константную, нельзя будет изменять элементы через `r[i]`.

Именно поэтому два варианта обычно объявляют **вместе**.

## 3.3. Проверка индекса: защита не только от падения программы

Массив `m_data[3]` имеет допустимые индексы `0`, `1`, `2`.

При `index == 3` чтение `m_data[index]` выходит за границу массива. При `index == 100` проблема та же. Такие обращения приводят к неопределённому поведению, а не обязательно к красивому сообщению об ошибке.

Поэтому перед обращением выполняется:

```cpp
if (index >= 3) {
    throw std::out_of_range("Invalid register index");
}
```

Почему именно `>= 3`, а не `> 3`? Потому что **индекс 3 уже недопустим**.

### Что с отрицательными индексами?

Параметр `std::size_t` — беззнаковый целочисленный тип. Он не содержит отрицательных значений.

Если попытаться передать `-1`, это значение преобразуется к беззнаковому типу и обычно становится очень большим числом. Проверка `index >= 3` всё равно отклонит его. Но в строгих настройках компилятора преобразование отрицательной константы может сопровождаться предупреждениями; выбирая API, необходимо учитывать контракт входных индексов.

Проверки вида `index < 0` **бессмысленны для `std::size_t`**. Мы уже сталкивались с такой ошибкой в упражнении `CMyString::erase`.

### Исключения и состояние объекта

Если проверка выполнена **до изменения массива**, то при недопустимом индексе объект остаётся прежним.

Идея переносится на более сложные операции: когда метод должен проверить сразу несколько аргументов, желательно убедиться в корректности всех необходимых условий **до первого изменения состояния**.

Например, если переставлять два элемента и сначала изменить один, а потом обнаружить недопустимый второй индекс, можно получить частично изменённый объект. Это плохо спроектированная операция.

## 3.4. `operator()` — объект, который можно вызвать как функцию

Скобки `()` в C++ могут означать не только вызов обычной функции. Пользовательский объект тоже может поддерживать синтаксис вызова:

```cpp
value = object(a, b);
```

Для этого в классе определяют `operator()`.

В отличие от `operator[]` в C++17, он может принимать **любое предусмотренное количество аргументов**.

Добавим в `TripleRegister` метод вычисления суммы двух регистров:

```cpp
int operator()(std::size_t first,
               std::size_t second) const {
    return (*this)[first] + (*this)[second];
}
```

Разбираем:

1. `int` перед именем — возвращаем число по значению. Вычисление суммы не должно давать право изменять внутренний регистр.
2. `operator()` — специальное имя оператора вызова.
3. Два индекса — обычные аргументы метода.
4. `const` после `()` разрешает вызов для константного объекта.
5. `*this` — сам объект. Вызов `(*this)[first]` переиспользует уже существующую проверку границ из `operator[]`.
6. Результаты чтения суммируются, затем возвращается новое значение.

```cpp
const TripleRegister r(4, 7, 11);
int sum = r(0, 2); // 15
```

Почему `(*this)` заключён в скобки? Потому что мы сначала разыменовываем `this`, получаем объект, а уже затем применяем к нему `[]`. Без нужных скобок можно получить иное связывание операций.

### Как это связано с многочленами и матрицами

Для многочлена полезна запись `p(x)`: объект представляет математическую функцию и умеет вычислять значение в точке `x`.

Для матрицы удобно `matrix(row, column)`: два индекса явно обозначают строку и столбец.

Эти идеи будут применяться в существующих заданиях `Polynomial2` и `Matrix2x2`. Здесь не приводим готовую реализацию их операторов, чтобы сохранить самостоятельную практику.

## 3.5. Временные объекты и опасные ссылки

Перегрузка часто создаёт временные результаты:

```cpp
Distance result = first + second;
```

Свободная функция `operator+`, возвращающая `Distance` по значению, создаёт результат, пригодный для дальнейшего использования. Возвращать из такого оператора ссылку на локальную переменную нельзя.

```cpp
// ОШИБКА: демонстрация опасной идеи, не используйте
const int& bad_reference() {
    int local = 42;
    return local;
}
```

После завершения функции `local` уничтожается. Ссылка на него становится недействительной.

Аналогично нельзя возвращать ссылку на временный локальный результат арифметической операции. Поэтому `operator+` в типичном интерфейсе возвращает **значение**, а `operator+=` — ссылку на **живой существующий объект**.

Очень важно различать:

- `T` — самостоятельное значение, которое можно безопасно хранить после завершения функции.
- `T&` — доступ к уже существующему объекту; его время жизни должно продолжаться.
- `const T&` — ссылка без права изменения через неё, но всё ещё зависящая от времени жизни объекта.

## 3.6. Полный пример использования двух операторов

К определению `TripleRegister` из раздела 3.2 добавим метод `operator()` из раздела 3.4 и посмотрим на `main`:

```cpp
#include <iostream>

int main() {
    TripleRegister registers(10, 20, 30);

    registers[1] = 50;
    std::cout << registers[1] << '\n'; // 50
    std::cout << registers(0, 2) << '\n'; // 40

    const TripleRegister fixed(3, 5, 7);
    std::cout << fixed[0] << '\n'; // 3
    std::cout << fixed(1, 2) << '\n'; // 12

    try {
        registers[3] = 100;
    }
    catch (const std::out_of_range& error) {
        std::cout << error.what() << '\n';
    }
}
```

В этом фрагменте у тебя уже сходятся сразу четыре темы: перегрузка, ссылки, `const` и исключения.

Создай класс `FixedHistory`, хранящий **ровно четыре целых значения** в обычном массиве-члене класса. Динамическая память не нужна.

Требования:

# Глава 4. Собственная строка `CMyString`: указатели, динамическая память и специальные операции

> **Это центральный практический пример исходной лекции (примерно слайды 12–23).** Здесь ты соединяешь операторную запись из предыдущих глав с владением ресурсом. Если понять этот раздел, станет гораздо легче написать вектор произвольного размера для лабораторной работы. В отличие от обычного математического класса, неверная операция копирования здесь может испортить память всей программы.

## 4.1. Что хранится в переменной `char*`

Рассмотрим запись:

```cpp
const char* text = "cat";
```

`text` — не массив из четырёх букв и не объект `std::string`. Это переменная, в которой находится **адрес первого символа** C-строки. Сама последовательность в памяти выглядит так:

```text
                  хранит адрес
text ───────────────────────────┐
                                ▼
                      +---+---+---+----+
                      | c | a | t | \0 |
                      +---+---+---+----+
                      0   1   2    3
```

Знак `\0` обозначает специальный символ с числовым кодом 0. Он **не является видимым символом текста**; C-функции используют его, чтобы обнаружить конец строки. В литерале `"cat"` три печатных символа, но для хранения нужны **четыре байта** при `sizeof(char) == 1` (по определению языка один `char` занимает один байт C++).

Проверь различие:

```cpp
#include <iostream>
#include <cstring>

int main() {
    char word[] = "cat";
    const char* p = word;

    std::cout << std::strlen(word) << '\n'; // 3
    std::cout << sizeof(word) << '\n';       // 4
    std::cout << sizeof(p) << '\n';          // размер указателя, не строки
}
```

`sizeof(word)` здесь известен компилятору, потому что `word` — реальный массив из четырёх элементов. А `sizeof(p)` сообщает размер **переменной-указателя**. По нему невозможно определить длину строки. `std::strlen` в свою очередь просматривает символы вплоть до первого нуля. Ей нужен корректный, доступный и завершающийся нулём массив символов; если нуля нет до конца выделенного буфера, чтение будет некорректным.

`char*` позволяет изменять доступные символы (если память действительно изменяемая), а `const char*` запрещает изменение через этот указатель. Особенно важно: **нельзя модифицировать строковый литерал**, даже если удалось получить неконстантный указатель небезопасным способом.

## 4.2. Арифметика адресов и почему возникает ошибка на один байт

Оператор `+` для указателя имеет иной смысл, чем сложение чисел: он сдвигает адрес на указанное число *элементов*, а не произвольных байтов.

```cpp
char data[] = "ABCDE";
char* p = data;

std::cout << *p << '\n';       // A
std::cout << *(p + 2) << '\n'; // C
std::cout << p[3] << '\n';     // D
```

`p[3]` и `*(p + 3)` — эквивалентные формы индексирования. Но обе корректны только если обращаются к существующему элементу. В нашем массиве есть элементы с индексами от 0 до 5 включительно, потому что шестой — `\0`; это **не означает**, что индексы 5 и выше являются символами логической строки.

Теперь буфер для склеивания двух C-строк:

```text
"home" — 4 символа
"work" — 4 символа
Результат "homework" — 8 символов + \0
Требуется минимум 9 элементов char
```

Ошибочный расчёт `strlen(left) + strlen(right)` забывает место под ноль. Результат может выглядеть нормальным в маленьком примере, но запись нуля выйдет за пределы выделенной памяти. Именно такие ошибки затем выявляются AddressSanitizer.

## 4.3. Функции `<cstring>`: что делает каждая

**`std::strlen(const char*)`** считает символы до первого `\0`, не считая сам ноль. Для пустой строки `""` возвращает 0. Она не знает размера выделенной памяти.

**`std::strcpy(destination, source)`** копирует C-строку **включая завершающий ноль**. Она не получает размер назначения и не проверяет, достаточно ли в нём места. При недостаточном буфере программа обращается за пределы массива. Для перекрывающихся диапазонов `strcpy` также непригодна.

**`std::strcat(destination, source)`** находит конец строки в `destination` и дописывает `source`, включая ноль. Назначение должно уже содержать корректную C-строку и иметь достаточно свободного места.

**`std::strcmp(first, second)`** сравнивает содержимое лексикографически: отрицательное значение означает `first < second`, ноль — равенство, положительное — `first > second`. Проверять следует **знак результата**, а не конкретное значение `-1` или `1`.

```cpp
#include <cstring>
#include <iostream>

int main() {
    const char* a = "apple";
    const char* b = "apricot";

    std::cout << std::strlen(a) << '\n';         // 5
    std::cout << (std::strcmp(a, b) < 0) << '\n'; // 1
    std::cout << (std::strcmp(a, a) == 0) << '\n';// 1
}
```

**`std::memcpy(destination, source, byte_count)`** переносит указанное количество байтов. Она не ищет `\0` и подходит не только для строк: можно копировать представление подходящих простых данных. При перекрытии исходного и целевого диапазонов результат неопределён.

**`std::memmove(destination, source, byte_count)`** также переносит байты, но корректно работает при перекрытии диапазонов. Это удобно при удалении символов внутри одного буфера:

```text
До:   H e l l o W o r l d \0
                    └── удаляем W o r
После: H e l l o l d \0 ...
```

Чтобы перенести хвост, нужно учитывать **байты после удаляемой части и завершающий ноль**, а также до операции убедиться, что оба диапазона допустимы. Если объект хранит собственную длину `m_size`, надёжнее рассчитывать длину переноса из неё, а не заново полагаться на `strlen`.

> **Условие для самостоятельной практики:** не используй `memcpy` там, где есть перекрытие. Если внутри массива возможны нулевые символы как обычные данные, `strlen` не измерит количество логических элементов объекта.

## 4.4. `malloc/free` и `new[]/delete[]`: ресурс должен иметь одного владельца

В исходных слайдах `CMyString` управляет памятью через C-подход: `malloc`/`free` и `strdup`. Чтобы читать эти слайды, нужно понимать правила:

```cpp
#include <cstdlib>

char* buffer = static_cast<char*>(std::malloc(16));
if (buffer == nullptr) {
    // Не удалось выделить память: обработать ошибку
} else {
    std::free(buffer);
}
```

`std::malloc` выделяет сырые байты и при неуспехе возвращает `nullptr`. Она не создаёт C++-объекты с вызовом их конструкторов. Для простого символьного буфера это возможно использовать, но при работе с объектами других типов ограничения становятся существенными.

В C++ чаще пишут:

```cpp
char* buffer = new char[16];
// ... работа с буфером
// Освобождение должно произойти даже при ошибках между этими строками.
delete[] buffer;
```

`new[]` выделяет память и создаёт элементы массива. При невозможности выделения память обычно сообщает об ошибке исключением `std::bad_alloc`. Парное освобождение — `delete[]`. Для одиночного объекта, созданного `new T`, используется `delete`, не `delete[]`.

| Чем выделили | Чем освобождаем |
|---|---|
| `std::malloc` | `std::free` |
| `new T` | `delete` |
| `new T[n]` | `delete[]` |
| `strdup` (POSIX) | `std::free` |

`strdup` — распространённая **POSIX**, но не стандартная функция ISO C++. Она выделяет новый буфер и копирует туда C-строку. Поэтому пример преподавателя со `strdup` следует понимать как платформенно-зависимый. Для переносимого C++17 можно выделить буфер самостоятельно и копировать необходимое число символов.

Ниже важнейшая мысль: **владелец ресурса отвечает за его освобождение**. Если два объекта считают себя владельцами одного буфера, их деструкторы попытаются освободить его дважды. Если ни один не считает себя владельцем, память утечёт.

## 4.5. Поверхностное и глубокое копирование

Предположим, объект хранит `char* m_data`, указывающий на динамический буфер. Если просто скопировать поле, получим:

```text
До копирования:
objectA.m_data ──> [ c | a | t | \0 ]

После ПОБИТОВОГО/ПОВЕРХНОСТНОГО копирования указателя:
objectA.m_data ──┐
                 ├──> [ c | a | t | \0 ]
objectB.m_data ──┘

После ГЛУБОКОГО копирования:
objectA.m_data ──> [ c | a | t | \0 ]
objectB.m_data ──> [ c | a | t | \0 ]
```

Во втором рисунке буферы выглядят одинаково, но находятся в разных участках памяти. Изменение одного не должно менять другой.

Три специальные операции образуют **правило трёх**:

1. Деструктор освобождает ресурс.
2. Конструктор копирования создаёт независимое представление ресурса.
3. Копирующее присваивание заменяет ресурс уже существующего объекта, не нарушая инварианты.

Чтобы разобрать механизм без готового решения проекта `CMyString`, рассмотрим **отдельный класс, хранящий массив целых чисел**:

```cpp
#include <cstddef>
#include <iostream>

class OwnedInts {
private:
    std::size_t m_count;
    int* m_data;

public:
    explicit OwnedInts(std::size_t count)
        : m_count(count),
          m_data(count == 0 ? nullptr : new int[count]{}) {}

    OwnedInts(const OwnedInts& other)
        : OwnedInts(other.m_count) {
        for (std::size_t i = 0; i < m_count; ++i) {
            m_data[i] = other.m_data[i];
        }
    }

    OwnedInts& operator=(const OwnedInts& other) {
        if (this == &other) {
            return *this;
        }

        int* replacement = other.m_count == 0
            ? nullptr
            : new int[other.m_count];

        for (std::size_t i = 0; i < other.m_count; ++i) {
            replacement[i] = other.m_data[i];
        }

        delete[] m_data;
        m_data = replacement;
        m_count = other.m_count;
        return *this;
    }

    ~OwnedInts() {
        delete[] m_data;
    }

    int& at(std::size_t index) {
        if (index >= m_count) {
            throw std::out_of_range("Invalid index");
        }
        return m_data[index];
    }

    std::size_t size() const {
        return m_count;
    }
};
```

Для этого примера дополнительно нужен `#include <stdexcept>`. Отдельно обрати внимание на порядок инициализации: `m_count` объявлен перед `m_data` и инициализируется первым. И на синтаксис конструктора копирования: `OwnedInts(const OwnedInts& other)`. Он вызывается **при создании нового объекта как копии**, тогда как `operator=` изменяет уже существующий.

Использование:

```cpp
OwnedInts a(2);
a.at(0) = 7;
OwnedInts b = a; // Создаётся независимый буфер
b.at(0) = 40;
std::cout << a.at(0) << ' ' << b.at(0) << '\n'; // 7 40

a = a; // Самоприсваивание не должно ломать объект
```

### Почему нельзя сначала делать `delete[] m_data`

Допустим, оператор присваивания сразу удаляет исходный буфер, а затем вызывает `new[]`. Если выделение новой памяти завершится исключением, объект останется без прежнего ресурса и может нарушить собственный инвариант. В примере выше **сначала** создаётся и заполняется `replacement`, и лишь затем освобождается прежний массив. Для массива `int` его копирование не выбрасывает исключений. Так можно обеспечить сильную гарантию: при ошибке исходный объект остаётся прежним.

Для произвольных пользовательских типов копирование элементов может выбрасывать исключения. Тогда нужно отдельно подумать об уничтожении уже созданных новых элементов и выделенного буфера. Этим объясняется, почему общий контейнер произвольного `T` — задача более высокого уровня, которую мы сможем полноценно решить после лекции о шаблонах.

> **Современное дополнение:** в производственном C++ такие ресурсы часто оборачивают в `std::unique_ptr` или контейнеры, чтобы избежать ручных `delete[]`. Но сейчас ручное владение изучается намеренно — оно потребуется в лабораторной.

## 4.6. Проектирование инварианта `CMyString`

Теперь возвращаемся к строковому классу преподавателя. На слайдах используются операции над собственным `char*`; в переносимой учебной модели удобно хранить также длину:

```cpp
class CMyString {
private:
    char* m_data;
    std::size_t m_size;

public:
    // Здесь ученик самостоятельно проектирует конструкторы,
    // операторы и деструктор в основном проекте.
};
```

**Инвариант** — условие, которое должно оставаться истинным в каждом корректном состоянии объекта. Один разумный контракт:

- `m_data` всегда указывает на выделенный массив хотя бы из одного `char`;
- `m_data[m_size]` равен `\0`;
- `m_size` отражает логическое число символов;
- буфером владеет только текущий объект;
- все методы сохраняют этот контракт или сообщают об ошибке, не разрушая объект.

Тогда пустая строка — не загадочное `nullptr`, а буфер `['\0']` с `m_size == 0`. Именно поэтому метод `c_str()` может возвращать корректный адрес даже для пустого объекта. В лекции преподавателя встречается и другая модель — пустая строка представлена нулевым указателем. Её тоже можно реализовать, но тогда каждый метод обязан отдельно обрабатывать этот случай. **Нельзя смешивать два контракта в одном классе.**

Если публичный изменяемый `operator[]` позволяет записать `\0` внутрь буфера, фактическая C-строка, видимая через `strlen`, будет короче `m_size`. Следовательно, методы должны заранее определить, допускаются ли внутренние нули, и при разрешении полагаться на сохранённую логическую длину. Такой выбор — часть проектирования интерфейса, а не просто синтаксическая деталь.

## 4.7. Операторы строкового класса: что они должны означать

В исходной лекции перечислены следующие операции:

| Запись | Учебный смысл | Главная сложность |
|---|---|---|
| `a = b` | заменить содержимое строки | глубокое копирование, самоприсваивание |
| `a == b` | сравнить тексты | сравнить символы, а не адреса |
| `a != b` | логическое отрицание равенства | повторное использование `==` |
| `s[index]` | получить/изменить символ | границы и ссылка на элемент |
| `a + b` | получить новую строку из двух | размер буфера и `\0` |
| `a += b` | дописать в существующую строку | самоалиасинг и сохранение ресурса |
| `s ^ count` | повторить текст `count` раз | переполнение размера и нулевое повторение |
| `!s` | получить строку в обратном порядке | не изменять исходную при возвращении нового значения |
| `static_cast<const char*>(s)` | получить адрес символов | время жизни буфера, неявное преобразование |
| `s(...)` | выбрать символы по индексам | проверить число и допустимость индексов |

Несколько важных вопросов, над которыми стоит подумать **до написания реализации**.

### Почему `==` не должен сравнивать `m_data == other.m_data`

Два объекта могут содержать одинаковый текст в **разных буферах**. Указатели при этом различны. Поэтому равенство строк определяется содержимым и длиной, а не совпадением адресов. Для обычных корректных C-строк `std::strcmp(...) == 0` проверяет содержимое, но если класс допускает внутренние нули, понадобится логика, учитывающая `m_size`.

### Почему `operator+` и `operator+=` решают разные задачи

`operator+` обычно возвращает **новый объект** и не меняет исходные строки. `operator+=` изменяет левый объект и возвращает ссылку на него. Важно заранее выбрать стратегию повторного использования операций, чтобы не дублировать выделение и копирование буферов без необходимости.

### Что может пойти не так в `s += s`

Источник и назначение совпадают. Если сначала освобождён прежний буфер, исходного текста больше нет. Даже если работа идёт внутри одного буфера, исходная и целевая области могут пересекаться. Необходимо заранее продумать последовательность действий или сохранить исходное содержимое до изменения буфера.

### Какой смысл у `!s` и `s ^ n`

В стандартных числовых типах `!` — логическое отрицание, а `^` — побитовое исключающее ИЛИ. Но в задаче преподавателя они имеют **специальную учебную семантику**: переворот строки и её повторение. Это допустимо как перегрузка для класса, однако в прикладном API такие неожиданные значения операторов могут снижать понятность кода.

Для повторения важно не только скопировать текст несколько раз, но и проверить, не переполняется ли вычисление будущей длины. Тип `std::size_t` — беззнаковый; арифметика переполнения для него оборачивается по модулю, а это может привести к выделению слишком маленького буфера. Проверку нужно проводить **до умножения**.

## 4.8. Преобразование к `const char*` и его цена

На слайде есть оператор:

```cpp
operator const char*() const;
```

Это *оператор преобразования типа*. У него нет отдельного указанного возвращаемого типа перед именем, как у обычной функции: целевой тип уже содержится в `operator const char*`. Для безопасного дизайна часто лучше иметь явный метод:

```cpp
const char* c_str() const;
```

В обоих случаях возвращённый адрес остаётся действительным только пока соответствующий буфер жив и не был заменён операцией объекта. Не следует сохранять указатель на содержимое временного строкового объекта и использовать его после уничтожения временного объекта.

Неявное преобразование к `const char*` может делать перегрузки неоднозначными или позволять неожиданным образом вызывать функции работы с указателями. Это одна из причин, по которым современный интерфейс часто предпочитает `c_str()`.

## 4.9. `operator()`: сколько аргументов и откуда их брать

В исходной лекции предлагается вариадическая форма:

```cpp
CMyString operator()(int count, ...) const;
```

Текст на слайде затем пытается добраться до аргументов через адрес параметра `count` и арифметику указателей. **Так делать нельзя:** стандарт C++ не гарантирует, что все аргументы вызова лежат подряд в памяти после `count`. В современных ABI часть аргументов часто передаётся через регистры; подобный код может дать неправильные значения или неопределённое поведение.

Если хочется сохранить интерфейс с многоточием, нужен стандартный механизм из `<cstdarg>`: `va_list`, `va_start`, `va_arg`, `va_end`. При этом вызывающая сторона должна передать именно столько аргументов ожидаемого типа, сколько заявлено, иначе безопасно проверить сам факт их существования невозможно.

Более удобный **современный вариант для практики** — `std::initializer_list<std::size_t>`:

```cpp
#include <initializer_list>

// Только объявление: реализация — в самостоятельном проекте.
CMyString operator()(std::initializer_list<std::size_t> indices) const;
```

Тогда вызов может выглядеть так:

```cpp
// В проекте при реализации корректного operator():
// CMyString result = source({5, 0, 2, 4});
```

Это позволяет явно передать набор индексов, пройтись по ним и проверить каждый. Однако **сам алгоритм выборки** и корректное выделение результирующего буфера ученик должен спроектировать самостоятельно.

## 4.10. Как проверять класс, который владеет памятью

Обычный пример `CMyString a("abc"); std::cout << a;` проверяет почти ничего. Реальный тест должен раскрывать ошибки, которые не видны на одном объекте:

1. Скопировать строку и изменить копию: оригинал не должен измениться.
2. Присвоить объект самому себе: данные не должны пропасть.
3. Склеить пустую и непустую строки в обоих порядках.
4. Проверить `s += s`: источник и назначение совпадают.
5. Проверить повторение строки ноль раз.
6. Проверить доступ к недопустимому индексу.
7. Создать и уничтожить несколько временных объектов.
8. Проверить, что после операции новая строка завершена `\0`.
9. При необходимости проверить поведение после неудачного выделения ресурса.

**Отсутствие видимого сбоя не означает отсутствия ошибки памяти.** AddressSanitizer и другие инструменты диагностики помогают обнаружить выход за буфер, использование освобождённой памяти и часть других ошибок. Утечки можно дополнительно проверять соответствующими средствами окружения.

В лабораторной особенно важно не только чтобы класс «работал», но и чтобы он оставался корректным при копировании, ошибках аргументов и уничтожении. Поэтому практика ниже будет включать многократную работу с объектами, а не только один успешный запуск.

## Самостоятельное закрепление главы 4: «Почему класс ломается после копирования?»

**Условие.** Дан небольшой `TextHolder`, который владеет символьным буфером и умеет показывать содержимое. При копировании объекта и последующем изменении одного из экземпляров возникают ошибки, а при завершении программы возможен сбой.

Требуется самостоятельно:

1. Указать, кому принадлежит буфер в каждом состоянии.
2. Объяснить, какой специальной операции класса не хватает и почему.
3. Исправить копирование и присваивание с учётом самоприсваивания.
4. Написать короткую локальную проверку независимости копий.
5. Объяснить, почему неверно рассчитывать длину буфера без места под `\0`.

В этой проверке не давай готового решения класса. Проверяй понимание времени жизни ресурсов, а не только совпадение вывода.

# Глава 5. Потоки: `operator<<`, `operator>>` и корректное поведение при ошибках

## 5.1. Почему потоки — часть интерфейса пользовательского класса

Число `int` можно вывести привычно:

```cpp
std::cout << 42;
```

А когда появляется собственный класс, хочется сохранить единый синтаксис:

```cpp
std::cout << value;
```

Для этого и перегружают операторы потокового вывода и ввода. Университетская лекция рассматривает их на последних слайдах 24–30.

Сразу различай четыре стандартных объекта:

- `std::cin` — стандартный поток ввода.
- `std::cout` — стандартный поток вывода.
- `std::cerr` — поток диагностических сообщений.
- `std::clog` — поток сообщений журнала.

Все они находятся в пространстве имён `std`, а не объявлены внутри твоих классов.

### Не путай «поток» с функциями C

По требованиям лабораторной ввод-вывод должен производиться средствами C++ (`std::cin`, `std::cout`), без `printf`, `scanf` и прямого использования C-потоков `stdin`/`stdout`.

Для тестирования нам дополнительно пригодятся `std::ostringstream` и `std::istringstream`: они работают с потоковым интерфейсом, но вместо консоли используют строку в памяти.

## 5.2. Синтаксис `operator<<` и зачем нужна ссылка на поток

Обычно оператор для собственного типа объявляют как **свободную функцию**:

```cpp
std::ostream& operator<<(std::ostream& out, const MyType& value);
```

Почему не как метод `MyType`? Потому что слева в выражении `std::cout << value` находится `std::cout`, то есть объект **стандартного потокового типа**, а не `MyType`. Чтобы определить оператор как метод, пришлось бы изменить стандартный класс, что мы делать не можем.

Здесь два параметра:

- `std::ostream& out` — ссылка на **тот поток, куда пишем**.
- `const MyType& value` — объект, который нужно вывести, без копирования и изменения.

Возвращаемый тип `std::ostream&` крайне важен.

```cpp
std::cout << a << " | " << b;
```

Это выражение выполняется примерно так:

```text
Шаг 1: operator<<(std::cout, a) возвращает std::cout
Шаг 2: возвращённый поток получает строку " | "
Шаг 3: тот же поток получает b
```

Если оператор ничего не возвращает, стандартная цепочка `<<` не получится. Возвращать поток по значению также нельзя: объекты стандартных потоков не являются обычными копируемыми значениями.

### Почему иногда нужен `friend`

Если поля класса приватные, свободная функция не может обращаться к ним напрямую. Есть два варианта:

1. Использовать публичные геттеры.
2. Объявить оператор дружественным и разрешить доступ к приватным полям.

Выбор зависит от дизайна. `friend` **не превращает свободную функцию в метод класса**.

## 5.3. Полный пример оператора вывода

Возьмём тип `Interval`, представляющий замкнутый числовой интервал с целыми границами. Его инвариант: левая граница не больше правой.

```cpp
#include <iostream>
#include <stdexcept>

class Interval {
private:
    int m_left;
    int m_right;

public:
    Interval(int left, int right)
        : m_left(left), m_right(right) {
        if (left > right) {
            throw std::invalid_argument("Invalid interval bounds");
        }
    }

    int left() const { return m_left; }
    int right() const { return m_right; }

    friend std::ostream& operator<<(std::ostream& out,
                                    const Interval& interval) {
        out << '[' << interval.m_left
            << ',' << interval.m_right << ']';
        return out;
    }
};

int main() {
    const Interval a(2, 7);
    const Interval b(10, 20);

    std::cout << a << " | " << b << '\n';
}
```

Ожидаемое содержимое консоли:

```text
[2,7] | [10,20]
```

Разбор важной строки:

```cpp
friend std::ostream& operator<<(std::ostream& out,
                                const Interval& interval)
```

- `friend` предоставляет доступ к двум приватным полям, но функция остаётся свободной.
- `std::ostream&` — результатом является тот же поток.
- `operator<<` — имя перегружаемого оператора.
- `std::ostream& out` — ссылка на уже существующий поток.
- `const Interval& interval` — интервал используется только для чтения.

Итоговая строка `return out;` возвращает ссылку на исходный поток и делает возможным последовательное применение `<<`.

## 5.4. Проверка вывода без консоли

Чтобы автоматически сравнить напечатанный формат, используют поток в строку:

```cpp
#include <sstream>
#include <string>

Interval interval(2, 7);
std::ostringstream stream;
stream << interval;

std::string result = stream.str();
// result == "[2,7]"
```

В этом примере `std::ostringstream` подходит к нашему `operator<<`, потому что он является выходным потоком. Мы не обязаны писать отдельный оператор только для консоли.

Это особенно важно для строгих тестов лабораторной: сравнивать можно **точную строку вывода**, а не полагаться на визуальное впечатление от консоли.

## 5.5. Как устроен `operator>>`

Оператор чтения обычно имеет форму:

```cpp
std::istream& operator>>(std::istream& in, MyType& value);
```

Отличия от вывода:

- Используется `std::istream`, а не `std::ostream`.
- Объект `value` передаётся через **изменяемую ссылку**: ввод должен записать новые данные.
- Возвращается ссылка на входной поток для поддержки `in >> a >> b`.

Не стоит автоматически писать симметричную сигнатуру с `const MyType&`: такой параметр невозможно изменить обычным присваиванием.

### Главная ловушка: частично изменённый объект

Представим, что пользователь вводит интервал в формате:

```text
[3,8]
```

Но присылает испорченный текст:

```text
[3;8]
```

Если оператор по мере чтения сразу меняет поля исходного объекта, может случиться следующее: первая граница уже стала 3, а потом выяснилось, что разделитель неверен. Объект оказался **частично обновлённым**.

Это плохой контракт, если мы обещали, что при ошибке старое значение сохраняется.

Надёжный порядок действий:

1. Прочитать все компоненты **во временные локальные переменные**.
2. Проверить, что поток успешно прочитал данные.
3. Проверить разделители и смысловые ограничения.
4. Только после успешных проверок присвоить новое значение исходному объекту.

## 5.6. Полный пример надёжного чтения `Interval`

Добавим к предыдущему классу дружественный оператор:

```cpp
friend std::istream& operator>>(std::istream& in,
                                 Interval& interval) {
    char open = '\0';
    char comma = '\0';
    char close = '\0';
    int left = 0;
    int right = 0;

    if (!(in >> open >> left >> comma >> right >> close)) {
        return in;
    }

    if (open != '[' || comma != ',' || close != ']' || left > right) {
        in.setstate(std::ios::failbit);
        return in;
    }

    interval = Interval(left, right);
    return in;
}
```

Здесь намеренно использована схема «сначала проверить, затем изменить». В нашей модели `Interval` состоит только из двух `int`, поэтому присваивание уже успешно сконструированного объекта достаточно простое.

### Разбор по шагам

**Шаг 1.** Объявляем локальные переменные:

```cpp
char open = '\0';
int left = 0;
```

Они не связаны с полями `interval`. Ошибка ввода не сможет случайно изменить существующий интервал через эти временные переменные.

**Шаг 2.** Пытаемся прочитать все части выражения:

```cpp
in >> open >> left >> comma >> right >> close
```

Это цепочка стандартных извлечений. Форматированное чтение обычно пропускает пробельные символы перед каждым таким извлечением, поэтому вход с пробелами между компонентами может успешно читаться.

**Шаг 3.** Если извлечение какого-либо компонента завершилось неудачно, условие `!(...)` обнаружит ошибку и оператор вернёт поток без изменения `interval`.

**Шаг 4.** Даже успешное чтение шести компонентов не гарантирует правильного формата: вместо запятой может стоять `;`, а левая граница может оказаться больше правой.

**Шаг 5.** При нарушении формата вызываем:

```cpp
in.setstate(std::ios::failbit);
```

Это переводит поток в состояние ошибки. Оно не равнозначно выбрасыванию исключения: стандартный поток обычно сигнализирует о сбое через своё состояние, если пользователь отдельно не настроил исключения потока.

**Шаг 6.** Только после полного успеха выполняем:

```cpp
interval = Interval(left, right);
```

До этой строки старое значение не трогали.

### Почему не нужно безусловно бросать `std::invalid_argument` из `operator>>`

Для некорректного **формата** потоковое извлечение обычно сообщает об ошибке через `failbit`. Для ошибочного **прямого вызова конструктора** `Interval(10,2)` уместно `std::invalid_argument`.

Это два способа сигнализации разных интерфейсов. Важно выбрать контракт и соблюдать его последовательно.

## 5.7. `fail()`, `eof()`, `clear()` и `std::istringstream`

Для проверки ввода без консоли удобно создавать поток из строки:

```cpp
#include <iostream>
#include <sstream>

int main() {
    Interval value(1, 2);
    std::istringstream good("[3,8]");
    good >> value;

    std::cout << value << '\n';   // [3,8]

    std::istringstream bad("[4;9]");
    bad >> value;

    std::cout << bad.fail() << '\n'; // 1
    std::cout << value << '\n';      // [3,8]
}
```

`fail()` показывает, находится ли поток в состоянии неуспешного извлечения.

`eof()` сообщает о признаке достижения конца входных данных. Эти состояния связаны, но **не одинаковы**: конец данных может быть достигнут при попытке читать следующий элемент; ошибка синтаксиса может возникнуть задолго до конца строки.

`clear()` сбрасывает флаги состояния потока, но **не меняет и не удаляет уже находящиеся во входе символы**. Поэтому для повторной попытки после ошибки иногда требуется также пропустить некорректный ввод. Не следует бездумно делать `clear()` и повторять ту же операцию, не анализируя положение чтения.

### `std::cout`, `std::cerr`, `std::clog`

Обычный результат программы направляют в `std::cout`. Диагностические сообщения часто выводят через `std::cerr`, а сообщения журнала — через `std::clog`. Во всех случаях сохраняется привычный синтаксис `<<`.

Для перевода строки чаще достаточно `\n`. Манипулятор `std::endl` дополнительно принудительно сбрасывает буфер, что не всегда нужно и может быть дороже.

## 5.8. Потоки и требования лабораторной

В лабораторной требуется потоковый вывод пользовательского класса и использование средств ввода-вывода C++. Кроме того, результат работы всех операторов и методов должен демонстрироваться в `main()`, а прикладные задачи выносятся из класса в самостоятельные функции.

Поэтому при подготовке своей практики ориентируйся на три вопроса:

1. **Можно ли вывести объект как значение, не меняя его?**
2. **Можно ли проверить формат вывода автоматически с помощью потока в строку?**
3. **Сохраняется ли правильное состояние объекта и потока, если вход некорректен?**

Эти проверки существенно серьёзнее, чем просто вывести пару чисел на экран.

## Закрепление после главы 5 · Форматируемое время `ClockTime`

> **Формат:** одна самостоятельная задача на 20–30 минут. Не показывать реализацию `operator>>` до попытки.

Создай класс `ClockTime`, представляющий время суток: часы от 0 до 23 и минуты от 0 до 59. Объект не должен существовать в некорректном состоянии.

Требования:

1. Конструктор принимает часы и минуты и проверяет диапазоны. Для некорректных аргументов используй подходящее исключение из `<stdexcept>`.
2. Реализуй `operator<<`, который печатает время в строгом формате `HH:MM`, например `07:05` и `23:59`.
3. Реализуй `operator>>`, читающий тот же формат. Отклоняй неправильные разделители, недопустимые часы и минуты, а также неполные данные.
4. При неудачном чтении установи состояние ошибки входного потока и сохрани **прежнее значение** `ClockTime`.
5. Поддержи цепочки `out << first << " | " << second` и `in >> first >> second`.
6. Проверь вывод через `std::ostringstream`, а ввод через `std::istringstream`.
7. При выборе форматирования объясни, какие манипуляторы могут изменять состояние потока и нужно ли восстанавливать его свойства после собственного оператора.

Обязательные случаи проверки:

- `07:05` — правильное время.
- `23:59` — правильное время.
- `24:00` — недопустимые часы.
- `12:60` — недопустимые минуты.
- `12;30` — неправильный разделитель.
- `12:` — незавершённое значение.
- При каждой ошибке уже существующий объект остаётся неизменным.

**Критерии:** корректная сигнатура обоих операторов; работа с `const`; точный формат с ведущими нулями; устойчивость к ошибкам; корректное состояние потока; отсутствие частичного изменения объекта; тестирование через строковые потоки.

# Итоги теории первой лекции

После пяти глав отдельные правила C++ должны сложиться в единую картину:

| Конструкция | Когда нужна | Что особенно важно |
|---|---|---|
| `T f() const` | Метод читает состояние | `const` относится к вызываемому объекту |
| `void f(T value)` | Нужна независимая копия | Изменения не затронут исходный объект |
| `void f(T& value)` | Нужно изменить исходный объект | Ссылка обозначает существующий объект |
| `void f(const T& value)` | Нужно читать без копии | Нельзя менять объект через этот параметр |
| `T operator+(...) const` | Новый результат операции | Обычно возвращаем по значению |
| `T& operator+=(...)` | Изменение левого операнда | Обычно `return *this` |
| `T& operator[](i)` | Изменяемый доступ к элементу | Возвращаем ссылку на живой элемент |
| `const T& operator[](i) const` | Чтение из константного объекта | Два `const` с разными ролями |
| `T operator()(...) const` | Объект ведёт себя как функция | Можно передать несколько аргументов |
| `std::ostream& operator<<(...)` | Потоковый вывод | Возвращаем тот же поток |
| `std::istream& operator>>(...)` | Потоковый ввод | Сохраняем старое состояние при ошибке |

## Почему эта лекция важна для лабораторной № 1

Лабораторная требует не демонстрации одной формулы, а **качественного пользовательского класса**: копируемого, владеющего ресурсом, с перегрузками сравнения и вывода, обработкой ошибочных аргументов, аккуратным стилем и компиляцией без предупреждений. Её задания для векторов, матриц и многочленов заметно сложнее сегодняшних учебных примеров, потому что предполагают произвольные размеры и шаблоны типов.

С самого начала полезно привыкать к лабораторным требованиям:

- Для GCC проверять `-Wall -Wconversion -Wextra -Wpedantic`; в тренажёре дополнительно может использоваться `-Werror`.
- Не создавать глобальные изменяемые переменные.
- Использовать английские имена и единый стиль.
- Не комментировать очевидное в каждой строке.
- Не использовать C-функции ввода-вывода вместо потоков C++.
- При ошибочных индексах и аргументах использовать подходящие исключения.
- Проверять, что публичный интерфейс согласован: `==` и `!=`, чтение и запись, изменяемые и константные версии методов.
- Предпочитать повторное использование уже реализованных операций вместо дублирования их логики.

**В этой лекции** мы реализуем ресурсный класс и вектор с компонентами `double`. Шаблонный вариант вектора произвольной размерности будет отдельным продолжением после изучения шаблонов в лекции № 3. Требования к качеству сигнатур и владению памятью действуют уже сейчас.
