### Класс CMyString

Класс самостоятельно владеет динамическим массивом символов.

Обязательные возможности:

- Пустая строка.
- Конструктор из `const char*`.
- Копирование.
- Присваивание.
- Деструктор.
- `size()`.
- `c_str() const`.
- Доступ к символам через `[]`.
- Константный `operator[]`.
- `==`, `!=`.
- `+`.
- `+=`.
- Потоковый вывод и ввод.
- Явный или неявный оператор преобразования к `const char*` — отдельное упражнение с обсуждением рисков.
- `operator!` для обращения порядка символов.
- `operator^` для повторения строки.
- `operator()` для выборки символов по индексам.
- `erase`.
- `replace_range`.

Для задания на вариадический оператор:

`CMyString s("abcdef");`

Вызов:

`s(4, 5, 0, 2, 4)`

должен давать `"face"`.

Первый аргумент обозначает количество индексов. Допустимо использовать `<cstdarg>`, но запрещён непереносимый трюк `&count + 1`.

Для `erase(position, count)`:

- Удалять без перевыделения памяти.
- Сохранять завершающий ноль.
- Не допускать выхода за диапазон.
- Разрешать `count = 0`.
- При ошибке не изменять объект.

Для `replace_range(position, count, replacement)`:

- Удалить указанную часть.
- Вставить новую последовательность.
- Поддерживать самоперекрытие.

Контрольный пример:

`CMyString s("ABCDE");`

`s.replace_range(1, 2, s.c_str() + 3);`

Результат: `"ADEDE"`.

- При `nullptr` выбрасывать `std::invalid_argument`.
- Проверять выход за границы.
- Проверять переполнение размера.
- По возможности обеспечивать сильную гарантию исключений.

# 3. Продолжительность и сложность интенсива

Рассчитать курс на **5 интенсивных дней по 4–6 часов**.

Если сложные задания потребуют дополнительного времени — не упрощать их ради расписания.

Каждый день содержит задания пяти разных типов.

### Тип Q — теоретические тесты

Не менее 12–15 вопросов на день.

Форматы:

- Один правильный ответ.
- Несколько правильных ответов.
- Правда/ложь.
- Выбор корректной сигнатуры.
- Определение ошибки компиляции.
- Сравнение поведения похожих конструкций.

Дистракторы должны быть реалистичными: варианты с `const`, неправильным `&`, неправильным возвращаемым типом, неверной специализацией и т. д.

Не использовать очевидно нелепые варианты.

### Тип S — синтаксические упражнения

Не менее 15 на день.

Пользователь пишет C++ по памяти, а не выбирает готовую строку из списка.

Обязательно проверять:

- Точный синтаксис.
- Допустимость компиляции.
- `const`-корректность.
- Ссылки.
- Тип результата.
- Область видимости.
- Требуемые заголовочные файлы.

Для нескольких синтаксических задач используй проверки через компиляцию, а не строгое сравнение с одной эталонной строкой. В C++ могут существовать несколько правильных записей.

### Тип P — предсказание поведения

Не менее пяти на день.

Примеры:

- Что выводит код?
- Какие методы вызываются?
- Сколько объектов создаётся и уничтожается?
- Какой тип `T` выводится?
- Как изменится состояние стека?
- Бросается ли исключение?
- Код корректен или содержит неопределённое поведение?

Не требуй предсказать конкретный результат там, где стандарт C++ его не гарантирует.

### Тип D — отладка

Не менее пяти на день.

Дай намеренно некорректный код. Я должен:

1. Найти проблему.
2. Объяснить причину.
3. Исправить её.
4. Пройти автоматические тесты.

Ошибки должны быть разных типов: синтаксис, логика, управление памятью, API, исключения, граничные случаи.

### Тип C — полноценное программирование

Не менее 3–5 задач на день, включая одну сложную.

Для каждого дня предусмотрены:

- A — базовые самостоятельные реализации.
- B — прикладные задачи.
- C — комплексная задача повышенной сложности.

**Задания B и C не считать необязательными для полного освоения.**

Допускается переходить к следующему дню с незакрытой задачей, но интерфейс обязан явно показывать этот пробел.

# 12. АВТОМАТИЧЕСКИЕ ТЕСТЫ

Для каждого программного задания подготовить:

### 1. Базовые тесты

Проверяют обычные примеры из условия.

### 2. Граничные тесты

Пустые значения, минимальные размеры, полная вместимость, неверные индексы.

### 3. Негативные тесты

Некорректные аргументы, ошибки ввода, неверные диапазоны.

### 4. Тесты типов и сигнатур

Проверки компиляции:

- `const`-объектов.
- Возвращаемого типа.
- Возможности цепочного присваивания.
- Корректности шаблонного вывода.
- Работающих перегрузок.

### 5. Тесты памяти

Для задач с ручным управлением памятью — санитайзеры, если доступны.

### 6. Сложные тесты

Несколько операций подряд, самоприсваивание, алиасинг, независимость копий, исключения.

**Не ограничивайся проверкой одного примера.**

В каждом полноценном практическом задании должно быть достаточно независимых проверок, чтобы поверхностное или ошибочное решение не проходило случайно.

Тесты должны проверять объявленный контракт. Не вводи скрытые требования, которых нет в условии.

### Изоляция

Если одно задание не компилируется, остальные должны оставаться доступными для проверки.

Невыполненные задачи ожидаемо могут давать FAIL. Это не означает, что сломана сама учебная платформа.

Создай отдельные smoke-тесты инфраструктуры и функциональные тесты решений.

# 13. СТРОГОЕ ОЦЕНИВАНИЕ

Не используй декоративную оценку.

Предложение шкалы:

| Результат | Статус |
|---|---|
| 0–49% | Тема не усвоена |
| 50–69% | Есть существенные пробелы |
| 70–84% | Базовое владение |
| 85–94% | Хорошее владение |
| 95–100% | Уверенное владение |

Но **один процент не должен автоматически означать освоение**.

Дополнительные обязательные условия:

- Критические ошибки памяти недопустимы.
- Undefined behavior недопустим.
- Программные задания должны компилироваться.
- Все обязательные тесты должны проходить.
- В заданиях на исключения должны проходить негативные тесты.
- В заданиях на шаблоны должны проверяться заявленные типы.
- В заданиях на копирование должна проверяться независимость объектов.

Если есть утечка памяти, нельзя поставить «Уверенное владение управлением ресурсами», даже если остальные проверки прошли.

Отдельно оценивай:

1. Знание синтаксиса.
2. Понимание поведения C++.
3. Самостоятельность реализации.
4. Корректность.
5. Работу с памятью.
6. Обработку ошибок.

### Защита от случайного успеха

Если пользователь допустил ошибки, а затем исправил их после просмотра подсказок, сохраняй отдельно:

- Первую попытку.
- Последнюю попытку.
- Количество подсказок.
- Число запусков тестов.

Не штрафуй за обучение, но не путай самостоятельное знание с решением после подробных подсказок.

Добавь повторную независимую проверку слабых тем на следующий день.
