# Глава 1. Шаблоны функций: от дублирования к выводу типа

## 1.1. Проблема, с которой начинается лекция

Представь, что требуется найти меньшее из двух чисел:

```cpp
int minimum(int first, int second) {
    return first < second ? first : second;
}
```

Теперь нужны `double`, `float`, `long` — алгоритм тот же, а типы параметров отличаются. Можно написать несколько перегрузок, но придётся поддерживать почти одинаковый код.

В презентации упоминается макрос:

```cpp
#define MINIMUM(a, b) ((a) < (b) ? (a) : (b))
```

Он не является функцией C++: препроцессор подставляет текст. Например, выражение с `++` может быть вычислено несколько раз. Макрос не задаёт строгих типов параметров, а отладка текстовых подстановок сложнее. Поэтому автор лекции переходит к шаблонам функций.

## 1.2. Синтаксис шаблона по элементам

```cpp
template <class T>
T minimum(T first, T second) {
    return first < second ? first : second;
}
```

- `template` объявляет шаблон, а не обычную функцию.
- `<class T>` задаёт **параметр типа** с именем `T`.
- Первый `T` в сигнатуре — возвращаемый тип.
- Второй и третий `T` — типы параметров.
- При использовании шаблона компилятор должен определить конкретный тип `T`.

Вместо `class` здесь можно написать:

```cpp
template <typename T>
```

Оба варианта равнозначны именно **в объявлении параметра типа**. Слово `class` не означает, что `T` обязан быть пользовательским классом: подойдут и `int`, и `double`, и классы с нужными операциями.

Имя `T` условно. Можно написать `template <typename Number>` и затем использовать `Number` во всём объявлении.

## 1.3. Когда компилятор создаёт конкретную функцию

```cpp
#include <iostream>

template <typename T>
T smaller(T left, T right) {
    return left < right ? left : right;
}

int main() {
    std::cout << smaller(12, 7) << '\n';    // 7
    std::cout << smaller(2.5, 8.0) << '\n'; // 2.5
}
```

Для первого вызова компилятор выводит `T = int`, для второго — `T = double`.

Этот процесс называют **инстанцированием шаблона**: компилятор создаёт нужные специализации на основе шаблонного описания. Это не процедура, которая в момент выполнения спрашивает пользователя, какой тип пришёл: обычные типы переменных известны при компиляции.

Условная схема:

```text
                    template<typename T>
                      T smaller(T, T)
                             |
          +------------------+------------------+
          |                                     |
        T = int                              T = double
    smaller<int>(int,int)             smaller<double>(double,double)
```

Не обязательно думать, что компилятор буквально создаёт два отдельных текстовых фрагмента в исходном файле: схема показывает семантику, а не устройство конкретного объектного файла.

## 1.4. Почему шаблон не подходит абсолютно любому классу

Посмотри на тело функции:

```cpp
return left < right ? left : right;
```

Здесь требуется сравнение `left < right`. Для целых и вещественных чисел оно допустимо. Для твоего собственного `CMyString`, если `operator<` не определён, шаблон не сможет создать корректную функцию.

Это важное правило: **шаблон не добавляет типу новые операции**. Он работает с теми типами, которые умеют выполнять необходимые операции. Именно поэтому предыдущая лекция об операторах напрямую связана с текущей.

Другой пример: шаблон обмена объектов должен уметь сохранять старое значение и присваивать новые. Если объект некопируемый, одна реализация может не подойти; для некоторых типов возможен перенос, но это уже дополнительный материал.

## 1.5. Ошибка вывода типа при смешанных аргументах

На слайдах 4–5 рассматривается:

```cpp
int whole = 3;
double fraction = 2.2;

// smaller(fraction, whole); // Ошибка вывода единого T
```

Шаблон объявлен как `T smaller(T, T)`. Из первого аргумента получается `T = double`, из второго — `T = int`.

Один параметр `T` не может одновременно означать два разных типа. Обычные неявные преобразования между `int` и `double` не устраняют автоматически этот конфликт именно **на этапе вывода типа T из двух параметров**.

Это не означает, что компилятор вообще не умеет преобразовывать `int` в `double`. Он умеет, но сначала должен быть выбран конкретный тип параметров шаблона.

## 1.6. Три решения из лекции

### Решение A. Явно преобразовать аргумент

```cpp
smaller(fraction, static_cast<double>(whole));
```

Теперь оба аргумента типа `double`. В презентации используется запись `(double)whole`; мы дополнительно показываем синтаксис `static_cast<double>(whole)`, который позже изучим отдельно.

### Решение B. Два независимых параметра типа

```cpp
template <typename First, typename Second>
First choose_smaller(First left, Second right) {
    return left < right ? left : right;
}
```

Такой шаблон принимает значения разных типов. Но **возвращает `First`**, и это принципиально.

Пример:

```cpp
int result = choose_smaller(10, 2.5);
```

Внутри сравнение выберет `2.5`, но тип результата — `int`, поэтому результат будет `2`. Вещественная часть потеряется. Сам факт успешной компиляции ещё не означает, что интерфейс правильно отражает математический смысл.

Можно вернуть `Second`, но проблема станет зеркальной. При проектировании обобщённой функции необходимо осознанно выбирать возвращаемый тип.

**Современное дополнение:** `std::common_type_t<First, Second>` из `<type_traits>` позволяет выразить общий тип многих пар значений, например `int` и `double`; это не универсальное решение для всех пользовательских классов и не исходный вариант из слайда.

### Решение C. Явно указать T

```cpp
smaller<double>(fraction, whole);
```

Здесь `<double>` — **аргумент шаблона**, а `(fraction, whole)` — **аргументы самой функции**. Благодаря `T = double` параметр для второго аргумента уже имеет тип `double`, и обычное преобразование целого значения допустимо.

Посмотри на отличие:

```cpp
smaller<int>(fraction, whole);
```

Этот вызов также может скомпилироваться, но `fraction` будет преобразован к `int`. В результате может потеряться дробная часть ещё **до сравнения**. Поэтому явно заданный тип влияет на поведение, а не только на синтаксис.

## 1.7. Параметры по ссылке в шаблонах

Твои ошибки в практиках часто были связаны не с идеей алгоритма, а с различием `T`, `T&` и `T*`.

Рассмотрим:

```cpp
template <typename T>
void inspect(const T& object) {
    // Только чтение без обязательной копии при передаче.
}
```

Если внутри функции нужно **изменить исходные объекты**, параметры по значению не подойдут:

```cpp
template <typename T>
void change_copy(T value) {
    value = T{}; // Меняется локальный параметр, а не исходный объект.
}
```

При `T&` операция относится к оригиналу:

```cpp
template <typename T>
void reset_value(T& value) {
    value = T{};
}
```

Но этот шаблон требует, чтобы `T` можно было создать без аргументов конструктора и присвоить. Он не обязан подходить всем классам.

### Ошибка указателя вместо сохранённого значения

Представим, что требуется поменять два объекта местами. Указатель на первый объект **не является его независимой копией**:

```cpp
T* saved_address = &first;
```

Если затем изменить `first`, доступ через `saved_address` увидит уже изменённый объект. А:

```cpp
T saved_value = first;
```

создаёт новый объект, который сохраняет прежнее значение. Именно это различие нужно помнить при обмене значениями, копировании ресурсов и сохранении состояния перед изменениями.

### Закрепление 1 — «Что компилятор должен вывести?»

**Формат:** одна составная самостоятельная проверка, около 15–25 минут.

Дан шаблон функции с единым `T`, объявленный учеником самостоятельно. Нужно:

1. Вызвать его с двумя `int` и двумя `double`.
2. Объяснить тип `T` для каждого вызова.
3. Вызвать с `double` и `int`, зафиксировать реальную ошибку компилятора.
4. Исправить вызов двумя способами без изменения шаблона.
5. Привести пример, когда выбор `T = int` вместо `T = double` меняет математический результат.
6. Кратко объяснить, какие операции должны поддерживать пользовательские типы, чтобы подойти для шаблона.

Не подставлять заранее все сигнатуры: проверка нацелена на самостоятельное восстановление синтаксиса.

# Глава 2. Перегрузка, специализация и шаблоны классов

## 2.1. Не всякий `<` означает сравнение содержимого

На слайдах 7–8 автор показывает C-строки:

```cpp
const char* first = "abcd";
const char* second = "abba";
```

Если универсальный шаблон использует `left < right`, то для `T = const char*` сравниваются **указатели**, а не символы строки. Для независимых объектов сравнение адресов встроенным `<` не является лексикографическим сравнением текста; соответствующий порядок не пригоден для выбора минимальной строки.

Нужна функция:

```cpp
#include <cstring>

std::strcmp(first, second);
```

`strcmp` возвращает отрицательное значение, если первая строка лексикографически меньше второй; ноль, если строки равны; положительное значение, если первая больше второй. Конкретная абсолютная величина отрицательного или положительного результата не важна.

Для `"abcd"` и `"abba"` первое различие находится на третьем символе: `c` больше `b`. Следовательно, меньше `"abba"`.

## 2.2. Перегрузка шаблонной функции обычной функцией

```cpp
#include <cstring>

template <typename T>
T smaller(T left, T right) {
    return left < right ? left : right;
}

const char* smaller(const char* left, const char* right) {
    return std::strcmp(left, right) < 0 ? left : right;
}
```

Последняя функция **не является шаблоном**. Это обычная перегрузка с тем же именем.

При `smaller(5, 8)` подойдёт шаблон. При `smaller(first, second)` компилятор рассматривает подходящие перегрузки. Когда обычная функция и вариант шаблона одинаково хороши по соответствию аргументов, преимущество получает обычная функция.

Важно не превращать это в неверное правило «любая обычная функция всегда выбирается раньше любого шаблона»: выбор перегрузки сначала учитывает допустимость кандидатов и качество преобразований аргументов.

## 2.3. Полная специализация шаблона функции

Другой способ со слайда 9 — специальная реализация **этого же шаблона** для конкретного `T`:

```cpp
#include <cstring>

template <typename T>
T smaller(T left, T right) {
    return left < right ? left : right;
}

template <>
const char* smaller<const char*>(const char* left, const char* right) {
    return std::strcmp(left, right) < 0 ? left : right;
}
```

Разберём запись:

- `template <>` — признак **полной специализации**.
- `smaller<const char*>` — явно заданное значение `T`.
- Параметры `const char*` и возвращаемый тип соответствуют исходному шаблону.
- Реализация использует `strcmp` вместо сравнения указателей.

Презентация показывает также пример для `char*`. Не путай `char*` и `const char*`: специализация для одного типа автоматически не становится специализацией для другого.

**Отличие от перегрузки:** специализация привязана к существующему шаблону и его сигнатуре; перегрузка — отдельная функция, которая участвует в выборе перегрузки. Не нужно одновременно добавлять в один тренировочный пример две конкурирующие реализации без понимания правил выбора.

Для `std::string` ситуация другая: класс поддерживает лексикографическое сравнение через `<`, поэтому исходный шаблон может работать без специальных перегрузок.

## 2.4. Шаблон класса: тип параметризует не только методы, но и поля

На слайде 10 автор переходит от шаблонных функций к шаблонным классам.

```cpp
template <typename T>
class Box {
private:
    T value_;

public:
    explicit Box(const T& value) : value_(value) {}

    const T& get() const {
        return value_;
    }
};
```

Использование:

Полная программа с тем же классом:

```cpp
#include <iostream>

template <typename T>
class Box {
private:
    T value_;

public:
    explicit Box(const T& value) : value_(value) {}
    const T& get() const { return value_; }
};

int main() {
    Box<int> a(10);
    Box<double> b(2.5);

    std::cout << a.get() << '\n'; // 10
    std::cout << b.get() << '\n'; // 2.5
}
```

Здесь `Box<int>` и `Box<double>` — разные конкретные типы, созданные из одного описания шаблона класса.

При `T = int` поле `value_` имеет тип `int`; при `T = double` — `double`. Таким образом, `T` влияет на **состав объекта**, а не только на тип входного параметра функции.

## 2.5. Параметры шаблона — не только типы

Автор перечисляет три вида параметров:

1. Параметры типов.
2. Константные параметры-значения.
3. Параметры-шаблоны.

В примере со стеком используется второй вид:

```cpp
template <typename T, int Capacity = 256>
class FixedStorage {
    T data_[Capacity];
};
```

Здесь `T` — тип элемента, а `Capacity` — целое значение, известное при компиляции.

```cpp
FixedStorage<int, 5> small;
FixedStorage<int, 20> large;
FixedStorage<double> default_storage; // Capacity = 256
```

Даже если `T` одинаковый, `FixedStorage<int, 5>` и `FixedStorage<int, 20>` — **разные типы**.

Нельзя подставить в параметр `Capacity` обычную переменную, значение которой считывается с клавиатуры во время выполнения. Шаблонный аргумент здесь должен быть допустимым константным выражением для C++17.

## 2.6. Почему `Class<T>::method` часто оказывается труднее самого алгоритма

Пусть внутри шаблонного класса объявлен метод:

```cpp
template <typename T>
class Box {
public:
    void set(const T& value);

private:
    T value_{};
};
```

Определение **вне** класса:

```cpp
template <typename T>
void Box<T>::set(const T& value) {
    value_ = value;
}
```

Разбор по частям:

- `template <typename T>`: сообщаем, что определение тоже относится к шаблону.
- `void`: возвращаемый тип метода.
- `Box<T>`: конкретизация шаблонного класса с теми же параметрами.
- `::`: оператор разрешения области видимости.
- `set`: имя метода, объявленного внутри `Box<T>`.
- `(const T& value)`: параметры метода, как в объявлении.

Писать `Box::set` без `<T>` для такого определения нельзя: `Box` — имя шаблона, и определяемый метод нужно отнести к соответствующей конкретизации.

### Если параметров два

```cpp
template <typename T, int Capacity>
bool FixedStorage<T, Capacity>::empty() const {
    // Обращение к внутренним полям класса.
    return true; // Только иллюстрация синтаксиса!
}
```

Здесь `Capacity` нужно указать **в двух местах**: в списке параметров шаблона и в `FixedStorage<T, Capacity>`.

Если значение по умолчанию `Capacity = 256` уже записано в объявлении класса, в определении метода снаружи его повторять не нужно.

Определения шаблонных методов обычно помещают в заголовочный файл (либо иной файл, включаемый из него), чтобы компилятор видел их при инстанцировании. Если спрятать обычное шаблонное определение в `.cpp` без явных инстанцирований, в другом файле могут появиться ошибки компоновки.

## 2.7. Стек, очередь и дек

Слайд 11 вводит три структуры:

- **Стек:** LIFO (*Last In, First Out*) — последним положили, первым сняли.
- **Очередь:** FIFO (*First In, First Out*) — первым положили, первым сняли.
- **Дек:** двусторонняя очередь — вставка и удаление возможны с обоих концов.

В этой лекции проектируем стек. Очередь и дек пока нужны только как контраст.

```text
Push(10)       Push(20)       Push(30)

[10]           [20]           [30] <- вершина
               [10]           [20]
                              [10]

Pop() возвращает 30, затем 20, затем 10.
```

## 2.8. Стек фиксированной вместимости: что означают `Size` и `m_cnt`

В презентации (слайд 12) используется класс вида:

```cpp
template <class T, int Size = 256>
class TFixedStack {
    T m_dat[Size];
    int m_cnt;
};
```

- `Size` — максимальное число элементов, заданное в типе.
- `m_cnt` — сколько элементов логически находится в стеке сейчас.

При `TFixedStack<int, 5>` массив имеет пять ячеек даже у пустого стека. Конструктор обычно устанавливает `m_cnt = 0`.

В примере лекции вставка использует:

```cpp
m_dat[m_cnt++] = data;
```

**Постфиксный** `m_cnt++` возвращает старое значение для индекса, а затем увеличивает счётчик.

Извлечение использует:

```cpp
data = m_dat[--m_cnt];
```

**Префиксный** `--m_cnt` сначала уменьшает счётчик, а затем выбирает элемент по обновлённому индексу.

Если сейчас `m_cnt == 3`, вершина лежит в `m_dat[2]`. Извлечение должно уменьшить `m_cnt` до 2 и скопировать элемент с индексом 2. Просмотр вершины (`Get`) использует `m_dat[m_cnt - 1]`, но **не уменьшает счётчик**.

### Ограничение фиксированного массива

Поле:

```cpp
T m_dat[Size];
```

создаёт массив объектов типа `T`. При обычном создании `TFixedStack<T, Size>` тип `T` должен допускать соответствующую инициализацию элементов массива — в примере лекции для пользовательских классов обычно нужен конструктор по умолчанию. Поэтому `TFixedStack<Polynomial2, 5>` может не скомпилироваться, если `Polynomial2` имеет только конструктор с тремя обязательными аргументами.

Также при `Push`, `Pop` и `Get` используются операции копирования и присваивания. Шаблон поддерживает лишь типы, для которых необходимые выражения корректны.

**Формат:** небольшое самостоятельное расширение, 20–30 минут.

Создай шаблон `LimitedStack<T, Capacity>` с массивом элементов и счётчиком. Не реализуй все методы сразу: сначала напиши самостоятельно:

4. Метод `full() const`.

Затем объясни, почему `LimitedStack<int, 3>` и `LimitedStack<int, 5>` имеют разные типы и почему чтение `Capacity` с клавиатуры здесь не подходит.

# Глава 3. Наследование шаблонов, динамический стек и специализация класса

## 3.1. Зачем нужен абстрактный интерфейс

Представим два способа хранить стек:

- Внутри массива фиксированной вместимости.
- В отдельных динамических узлах связного списка.

Пользователь стека не обязан знать, как именно организовано хранение. Ему нужны операции: добавить, извлечь, посмотреть вершину.

На слайде 14 преподаватель предлагает шаблонный абстрактный класс:

```cpp
template <typename T>
class StackInterface {
public:
    virtual ~StackInterface() = default;

    virtual bool push(const T& value) = 0;
    virtual bool pop(T& value) = 0;
    virtual bool peek(T& value) const = 0;
};
```

Разбор:

- `template <typename T>` — интерфейс тоже зависит от типа элемента.
- `virtual` — метод может вызываться через базовую ссылку с учётом реального типа объекта.
- `= 0` — чисто виртуальная функция: базовый класс не даёт обычной реализации этого действия.
- `virtual ~StackInterface()` — позволяет корректно уничтожить производный объект через указатель на базовый класс.

Класс с чисто виртуальными методами, не получившими реализацию, нельзя непосредственно создать как объект. Но можно создать производный класс, реализующий интерфейс.

## 3.2. Наследование шаблонного интерфейса

```cpp
template <typename T, int Capacity = 10>
class FixedStack : public StackInterface<T> {
    // Конкретная реализация.
};
```

Здесь важна запись:

```cpp
: public StackInterface<T>
```

Она означает, что `FixedStack<int, 5>` — разновидность `StackInterface<int>`, а `FixedStack<double, 10>` — разновидность `StackInterface<double>`.

Значение `Capacity` нужно производному классу, но **не нужно базовому интерфейсу**, так как интерфейс описывает операции, а не способ размещения элементов.

Методы производного класса помечают `override`, чтобы компилятор проверял правильность переопределения:

```cpp
bool push(const T& value) override;
```

Например, если в базовом классе `peek(T&) const`, а в производном забыть `const`, метод не будет соответствовать исходной сигнатуре; `override` позволит обнаружить проблему при компиляции.

## 3.3. Полиморфизм: один интерфейс — два способа хранения

Можно написать внешнюю функцию:

```cpp
template <typename T>
void add_two(StackInterface<T>& stack, const T& first, const T& second) {
    stack.push(first);
    stack.push(second);
}
```

Эта функция не знает, использует ли стек массив или связный список. Конкретный виртуальный метод выбирается во время выполнения в соответствии с реальным типом объекта.

Обрати внимание: **тип `T` здесь определён при компиляции**, а конкретная реализация виртуального метода выбирается полиморфно во время выполнения. Эти механизмы не противоречат друг другу; они отвечают на разные вопросы.

## 3.4. Динамический стек на односвязном списке

На слайде 15 преподаватель показывает вложенную структуру узла:

```cpp
template <typename T>
class LinkedStack {
    struct Node {
        T data;
        Node* link;
    };

    Node* head_ = nullptr;
};
```

Каждый узел содержит:

- `data` — значение элемента.
- `link` — адрес следующего узла или `nullptr`.

Схема:

```text
head_ ---> [30 | next] ---> [20 | next] ---> [10 | nullptr]
           вершина
```

Динамический стек не хранит заранее массив из `Capacity` элементов. Узлы создаются по мере добавления; вместимость ограничена доступной памятью и возможностями реализации, а не постоянным параметром шаблона.

### Что происходит при добавлении

Логика состоит из подготовки узла, установки связи с прежней вершиной и обновления `head_`.

**Порядок важен:** сначала нужно сохранить возможность добраться до старой цепочки. Если потерять старый `head_`, все узлы ниже вершины окажутся недоступными — утечка памяти.

На слайде преподавателя встречается сочетание `new list` и последующего присваивания `p->data = data`. Оно требует, чтобы `T` можно было создать без аргументов, и должно учитывать исключения при присваивании. В современных вариантах иногда создают узел **с уже инициализированным значением**, но не раскрывай этим готовую реализацию самостоятельного проекта целиком.

### Что происходит при извлечении

Нужно:

1. Проверить, не пуст ли стек.
2. Получить значение вершины.
3. Переместить `head_` к следующему узлу.
4. Освободить старую вершину.

Если передача значения наружу (`T` может иметь бросающий `operator=`) завершилась исключением, желательно не успеть разрушить список. Именно поэтому порядок присваивания, обновления ссылки и удаления узла имеет значение.

### Уничтожение

Деструктор последовательно проходит цепочку от головы, освобождая все узлы. Просто `delete head_` по умолчанию освободит только головной узел, если у `Node` нет специальной рекурсивной логики владения. Нельзя терять доступ к оставшейся части списка до её освобождения.

## 3.5. Копирование связного стека

У класса с полем `Node* head_` возникает та же проблема, что у `CMyString` и `DynamicVector`: обычное копирование указателя не создаёт копий узлов.

Если две копии будут освобождать одну цепочку, появится двойное освобождение. Для полноценного копируемого стека требуется **глубокое копирование всей цепочки с сохранением порядка элементов**.

Проверь следующие условия:

- Создание независимой копии.
- Изменение одного стека не затрагивает другой.
- Самоприсваивание.
- Корректность пустого стека.
- Безопасное освобождение при ошибке копирования одного из элементов.

Для учебного интерфейса разрешено выбрать либо явный запрет копирования, либо реализацию правила трёх. Но **в нашем итоговом проекте лабораторного уровня требуется глубокое копирование**, поскольку преподаватель требует копируемые ресурсные классы.

## 3.6. Определение метода вне шаблонного класса

Слайд 16 специально подчёркивает эту форму:

```cpp
template <typename T>
bool LinkedStack<T>::pop(T& value) {
    // Тело реализует работу со списком.
    return false; // Заглушка здесь дана только для показа записи.
}
```

Частая ошибка — забыть `<T>` после имени класса:

```cpp
// Неверная форма для данного шаблона:
// bool LinkedStack::pop(T& value) { ... }
```

Другая ошибка — написать `template <typename T>` только перед объявлением класса, а перед внешним определением забыть. Это отдельное определение, ему снова нужен список параметров шаблона.

## 3.7. Специализация шаблонного класса для C-строк

На слайде 17 преподаватель показывает полную специализацию динамического стека для `char*`.

Почему её вообще рассматривают? Потому что обычный шаблон `LinkedStack<char*>` хранит **указатели**, не собственные копии строк. Если вызывающий код освободит исходную C-строку, в стеке останется висячий адрес.

Специализированный класс может изменить модель владения:

```cpp
template <>
class LinkedStack<char*> : public StackInterface<char*> {
    // Специальная семантика владения строками.
};
```

В слайдах используются `strdup` и `free`; это POSIX-подход. Если строка выделена `strdup`, обычное освобождение должно идти через `free`.

**Не копируй пример как законченный безопасный класс без проверки.** Для реальной специализации следует продумать:

- Кто владеет каждой копией строки.
- Что делает `push` при ошибке выделения памяти.
- Что делает `pop`: возвращает новую копию, отдаёт владение или только читает данные.
- Когда освобождаются строки внутри узлов.
- Что делает `peek` и на какое время валиден указатель.
- Как работает копирование всего специализированного стека.

Если проект требует абсолютной безопасности, пользовательский тип `std::string` часто проще, однако в учебной задаче важно понять именно владение `char*`.

## 3.8. Специализация отдельного метода

Слайд 18 показывает другую форму:

```cpp
template <>
bool LinkedStack<char*>::push(char* const& value) {
    // Особая реализация метода для T = char*.
    return false; // Синтаксическая иллюстрация, не готовая логика.
}
```

Это **полная специализация одного метода**, а не полная специализация класса.

Указанный параметр имеет вид `char* const&`: при подстановке `T = char*` в `const T&` получаем **константную ссылку на указатель**, а не `const char*&`. Здесь `const` относится к самому значению указателя; он не запрещает менять символы по адресу.

Этот нюанс важен для понимания шаблонного синтаксиса: `const T&` не всегда означает то же самое, что кажется при мысленном чтении `const char*`.

Не смешивай в одном упражнении полную специализацию класса и внешнюю специализацию метода так, будто это обязано существовать одновременно: это альтернативные способы проектирования.

# Глава 4. Приведение типов и RTTI

## 4.1. Зачем вообще нужно преобразовывать типы

На слайде 20 показано целочисленное деление:

```cpp
#include <iostream>

int main() {
    int a = 5;
    double first = a / 2;
    double second = static_cast<double>(a) / 2;

    std::cout << first << '\n';  // 2
    std::cout << second << '\n'; // 2.5
}
```

Почему `first == 2.0`? Потому что `a / 2` выполняется как деление двух `int`: получается целочисленный результат 2; затем он превращается в `double`.

В выражении `static_cast<double>(a) / 2` преобразование происходит **до деления**. Теперь в операции участвует `double`, поэтому результат 2.5.

На слайде используется запись `(double)a` и отдельно обсуждается `double(a)`. В C++17 полезно также знать более явные именованные приведения типов.

## 4.2. `static_cast`

Синтаксис:

```cpp
static_cast<TargetType>(expression)
```

Для чисел:

```cpp
#include <iostream>

int main() {
    double number = 3.9;
    int whole = static_cast<int>(number);
    std::cout << whole << '\n'; // 3
}
```

Дробная часть при преобразовании к `int` отбрасывается в сторону нуля (когда результат представим целым типом). Нельзя автоматически предполагать, что числовое преобразование всегда сохраняет информацию.

`static_cast` также может выполнять некоторые преобразования внутри иерархии классов. Но при преобразовании от базового указателя к производному **не проверяет реальный динамический тип объекта**, в отличие от `dynamic_cast`.

## 4.3. `const_cast`

Синтаксис:

```cpp
const_cast<TargetType>(expression)
```

Его используют для изменения `const`- или `volatile`-квалификации указателя/ссылки, где такое преобразование допустимо.

```cpp
#include <iostream>

int main() {
    int value = 10;
    const int* read_only_view = &value;
    int* writable_view = const_cast<int*>(read_only_view);

    *writable_view = 20;
    std::cout << value << '\n'; // 20
}
```

Почему пример допустим? Потому что **сам объект `value` изначально изменяемый**. Лишь один способ доступа к нему был через `const int*`.

Но:

```cpp
const int value = 10;
int* pointer = const_cast<int*>(&value);
// *pointer = 20; // Не выполнять: неопределённое поведение.
```

`const_cast` **не превращает реально константный объект в изменяемый**. Наличие оператора не оправдывает запись в исходный `const`-объект.

## 4.4. `reinterpret_cast`

Этот оператор предназначен для низкоуровневых преобразований между определёнными типами указателей и некоторыми целочисленными типами.

```cpp
#include <cstddef>

int main() {
    int number = 42;
    const unsigned char* bytes =
        reinterpret_cast<const unsigned char*>(&number);

    unsigned char first_byte = bytes[0];
    (void)first_byte;
}
```

Обращение к представлению объекта через `unsigned char` допускается стандартом. Но **значение первого байта зависит от представления целого числа на данной машине**. Не делай из этого переносимую проверку на конкретное число.

`reinterpret_cast` **не выполняет обычное числовое преобразование**. Он не предназначен для превращения `double 3.5` в `int 3` — для этого нужен другой механизм.

Неправильное применение `reinterpret_cast` может создать указатель, который нельзя безопасно разыменовать. На практике это низкоуровневый инструмент, а не замена `static_cast`.

При необходимости хранения численного представления адреса используют типы вроде `std::uintptr_t` из `<cstdint>` при их наличии, но это не делает любые преобразования и обратное разыменование универсально безопасными.

## 4.5. Статический и динамический типы

Представим классы:

```cpp
class Shape {
public:
    virtual ~Shape() = default;
};

class Rectangle : public Shape {};
class Circle : public Shape {};
```

Создаём:

```cpp
Rectangle rectangle;
Shape* shape = &rectangle;
```

- Статический тип переменной `shape` — `Shape*`.
- Фактический тип объекта, на который указывает `shape`, — `Rectangle`.

В иерархии полиморфных классов эти два факта могут различаться. Иногда нужно узнать, к какому производному классу принадлежит объект, имея только базовый указатель или ссылку.

## 4.6. `dynamic_cast`: проверяемое приведение

```cpp
#include <iostream>

class Shape {
public:
    virtual ~Shape() = default;
};

class Rectangle : public Shape {};
class Circle : public Shape {};

int main() {
    Rectangle rectangle;
    Shape* base = &rectangle;

    Rectangle* match = dynamic_cast<Rectangle*>(base);
    Circle* mismatch = dynamic_cast<Circle*>(base);

    std::cout << (match != nullptr) << '\n';    // 1
    std::cout << (mismatch == nullptr) << '\n'; // 1
}
```

Первый `dynamic_cast` успешен: реальный объект — `Rectangle`. Второй неуспешен: объект не `Circle`, поэтому возвращается `nullptr`.

При соответствующих преобразованиях вниз по иерархии необходима **полиморфная база**, то есть класс хотя бы с одной виртуальной функцией. В примере это виртуальный деструктор.

Важно, что `dynamic_cast` работает с **указателями или ссылками**, а не просто с произвольными значениями классов.

### `dynamic_cast` для ссылки

При неудачном преобразовании ссылки нельзя вернуть `nullptr`, потому что результат имеет тип ссылки. Поэтому выбрасывается `std::bad_cast`:

```cpp
#include <iostream>
#include <typeinfo>

class Base {
public:
    virtual ~Base() = default;
};
class DerivedA : public Base {};
class DerivedB : public Base {};

int main() {
    DerivedA a;
    Base& base = a;

    try {
        DerivedB& wrong = dynamic_cast<DerivedB&>(base);
        (void)wrong;
    } catch (const std::bad_cast&) {
        std::cout << "Not a DerivedB\n";
    }
}
```

Это прямая связь с переходным уроком об исключениях.

## 4.7. `typeid` и RTTI

RTTI означает *Run-Time Type Information* — получение информации о типе во время выполнения.

Оператор `typeid` объявлен в `<typeinfo>`:

```cpp
typeid(expression)
typeid(TypeName)
```

Для полиморфного объекта, доступного как базовая ссылка/разыменованный базовый указатель, `typeid` может дать фактический динамический тип.

```cpp
#include <iostream>
#include <typeinfo>

class Shape {
public:
    virtual ~Shape() = default;
};
class Rectangle : public Shape {};

int main() {
    Rectangle rectangle;
    Shape* shape = &rectangle;

    std::cout << (typeid(*shape) == typeid(Rectangle)) << '\n'; // 1
    std::cout << (typeid(shape) == typeid(Shape*)) << '\n';      // 1
}
```

Разница принципиальна:

- `typeid(shape)` смотрит на **сам указатель**; его тип `Shape*`.
- `typeid(*shape)` смотрит на **полиморфный объект**; в примере это `Rectangle`.

Для `typeid(*pointer)` с разыменованием нулевого указателя на полиморфный тип может выбрасываться `std::bad_typeid`. Не нужно экспериментировать с разыменованием произвольных недействительных указателей.

Метод `typeid(...).name()` существует, но его текстовый результат зависит от компилятора; не сравнивай имена типов как строки, чтобы управлять основной логикой программы.

## 4.8. Чем отличается `dynamic_cast` от `static_cast`

Предположим, у нас есть `Shape* base`, который иногда указывает на `Rectangle`, иногда на `Circle`.

- `static_cast<Rectangle*>(base)` может скомпилироваться без проверки того, является ли реальный объект `Rectangle`. Дальнейшее использование неправильного результата опасно.
- `dynamic_cast<Rectangle*>(base)` проверяет совместимость **во время выполнения** и сообщает о неудаче через `nullptr`.

Для обычного преобразования `double` в `int` нужен не `dynamic_cast`, а `static_cast`.

Выбор оператора определяется **характером задачи**, а не предпочтением использовать «самый сильный» механизм.

## 4.9. Важнейшая связь с лабораторной № 1

В лабораторной преподаватель **прямо запрещает выбор поведения по фактическому типу данных во время выполнения** (например, через `typeid`, `dynamic_cast`, теги/enum типа) вместо шаблонов и перегрузки.

Это не означает, что `dynamic_cast` запрещён в C++ вообще. Мы изучаем его для понимания языка и работаем с ним в отдельной учебной задаче. Но когда придёт время реализовывать `DynamicVector<T>` или шаблонный стек из лабораторной, решения для разных типов данных следует проектировать преимущественно **на этапе компиляции**: через шаблоны, перегрузку и допустимые специализации.

Один и тот же материал лекции учит нас **двум разным механизмам**:

- Параметр `T` определяет тип данных при компиляции.
- Виртуальные функции и некоторые операции RTTI анализируют полиморфный объект при выполнении.

Не путай их роли.

# Заключение и маршрут к лабораторной

За третью лекцию ты познакомился с тремя уровнями обобщения и выбора поведения:

1. **Шаблон функции:** один алгоритм для типов, поддерживающих нужные операции.
2. **Шаблон класса:** одно устройство структуры данных для разных `T` и других параметров шаблона.
3. **Полиморфизм и RTTI:** работа с объектами иерархии через общий базовый интерфейс и, где необходимо, проверка динамического типа.

Для первой лабораторной критичны точные сигнатуры, ручное владение ресурсом, копируемость и использование шаблонов **вместе**. Поэтому самостоятельная практика устроена так:

- **Проект 1:** шаблонные функции и особая обработка C-строк — вывести типы, выбрать корректные ссылки и тип результата, применить специализацию или перегрузку.
- **Проект 2:** шаблонный стек фиксированной вместимости — закрепить синтаксис `template <typename T, int Capacity>` и определения методов вне класса, граничные случаи LIFO.
- **Проект 3:** копируемый динамический стек с абстрактным интерфейсом — связные узлы, глубокое копирование, исключения, виртуальный деструктор и обработка через `IStack<T>&`. **Прикладной финальный этап этого же проекта** — вычисление выражения в постфиксной записи с помощью созданного стека. Это адаптация задачи № 3 варианта «Стек» из первой лабораторной работы, а не новая четвёртая большая работа.

Отдельный короткий проверочный файл для RTTI закрепляет приведённые операторы и не превращает их в обязательный механизм реализации шаблонного стека.

Компиляция выполняется **локально на твоём компьютере**. Сайт показывает готовую теорию, постановки проектов, обычные проверочные `main.cpp` и хранит прогресс без имитации запуска C++.
