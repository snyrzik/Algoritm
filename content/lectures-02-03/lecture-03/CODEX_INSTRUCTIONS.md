## Проект 1. Шаблонные алгоритмы и строки

Предоставь только **условие и `MAIN_GENERIC_FUNCTIONS.cpp`**, но не готовый `GenericAlgorithms.h`.

Ученик должен самостоятельно написать заголовочный файл `GenericAlgorithms.h` с:

```cpp
template <typename T>
T maximum(T a, T b);

template <typename T>
void swap_values(T& a, T& b);

template <typename T>
T minimum_of_three(T a, T b, T c);

template <typename T>
std::size_t index_of_min(const T* data, std::size_t size);
```

Дополнительно:

1. **Полная специализация** `maximum<const char*>` для лексикографического сравнения C-строк через `std::strcmp`.
2. **Обычная перегрузка** `const char* minimum_value(const char*, const char*)`, тоже сравнивающая содержимое строк.
3. Для `index_of_min`: `nullptr` вызывает `std::invalid_argument`; при ненулевом указателе и `size == 0` — `std::out_of_range`; при повторяющемся минимуме возвращается **индекс первого вхождения**.
4. `swap_values` меняет исходные объекты и работает с пользовательским копируемым классом; самоприменение `swap_values(x, x)` не повреждает `x`.
5. `minimum_of_three` обрабатывает случаи равенства и всегда возвращает значение для указанных в условиях поддерживаемых типов.
6. `maximum` для обычного `T` требует поддержки `operator<`; не делай вид, что он подходит к любому возможному типу. В варианте с одним `T` смешанные аргументы не обязаны выводиться автоматически.

Согласование интерфейса: отдельно показать примеры вызовов из `main`, но **не раскрывать алгоритм**. Пользователь должен сам написать `template`, `template <>`, нужные параметры и возвращаемые типы. Эта работа специально закрепляет различие между шаблоном, обычной перегрузкой и специализацией.

## Проект 2. FixedStack<T, Capacity>

Реализация в `FixedStack.h` целиком видна компилятору. Точный интерфейс:

```cpp
template <typename T, int Capacity = 256>
class FixedStack {
public:
    FixedStack();
    bool push(const T& value);
    bool pop(T& out);
    bool peek(T& out) const;
    std::size_t size() const;
    bool empty() const;
    bool full() const;
};
```

- `Capacity > 0` — зафиксированное требование. Можно обеспечить через `static_assert`.
- Реализация основана на массиве `T data_[Capacity]` и логическом счётчике. Для этой реализации `T` должен быть доступно конструируемым по умолчанию и копируемым/присваиваемым, как требуется методами.
- При переполнении `push` возвращает `false` и не меняет стек.
- При пустоте `pop`/`peek` возвращают `false` и не меняют аргумент `out`.
- При успехе `pop` извлекает вершину и уменьшает размер; `peek` возвращает вершину без удаления.
- Поведение LIFO обязательно.
- Минимум **три метода определить вне тела класса**, используя `template <typename T, int Capacity>` и `FixedStack<T, Capacity>::method`. Определения могут оставаться в том же заголовке.
- При исключении из присваивания `T` сохранять по крайней мере корректный объект без утечек; для `pop` не удалять вершину до успешной передачи значения наружу.

Локальный проверочный файл — `MAIN_FIXED_STACK.cpp`.

## Проект 3. Абстрактный интерфейс и копируемый связный стек

Это основной сложный проект лекции № 3, одновременно готовящий к требованиям лабораторной по владению ресурсом и шаблонам.

Создай условие для трёх заголовков ученика:

- `IStack.h`
- `LinkedStack.h`
- доработка `FixedStack.h`

Интерфейс:

```cpp
template <typename T>
class IStack {
public:
    virtual ~IStack() = default;
    virtual bool push(const T& value) = 0;
    virtual bool pop(T& out) = 0;
    virtual bool peek(T& out) const = 0;
    virtual std::size_t size() const = 0;
};
```

`LinkedStack<T> : public IStack<T>` должен:

- Хранить элементы в собственных динамических узлах односвязного списка.
- Быть корректно **копируемым**: конструктор копирования и оператор присваивания должны делать глубокую копию с сохранением порядка LIFO; самоприсваивание корректно.
- Иметь деструктор, который освобождает все узлы.
- Поддерживать `push`, `pop`, `peek`, `size`.
- Не требовать от `T` конструктора по умолчанию **для хранения узлов**. Примеры проверяются также на `NoDefault`.
- Не менять стек при неудаче создания нового узла.
- Не удалять вершину до успешной передачи значения наружу при `pop` (для копирующего присваивания `T`, которое может бросать исключение).
- Возвращать `false` для пустого `pop`/`peek`; значение `out` при неудаче не менять.
- Использовать правильную семантику `const` и виртуальных методов.

В рамках этого же проекта доработать `FixedStack<T, Capacity>` из предыдущего проекта так, чтобы он **наследовался от `IStack<T>`** и реализовывал виртуальные методы с `override`. Его прежний `MAIN_FIXED_STACK.cpp` должен продолжить работать.

Дополнительно написать внешнюю шаблонную функцию, принимающую `IStack<T>&` и вызывающую операции стека, не зная конкретной реализации. В приложенном `MAIN_LINKED_STACK.cpp` такая внешняя функция для проверки уже предоставлена, но не является реализацией самих классов.

Условие проекта должно требовать объяснить:

- Почему копирование одного только указателя головы списка не создаёт копию стека.
- Как сохраняется порядок элементов.
- Почему деструктор базового класса должен быть виртуальным.
- Почему поведение типа `T` и виртуальный вызов решения стека относятся к разным этапам.
- Почему в лабораторной нельзя заменить шаблоны проверкой `typeid` для выбора арифметики.

Тест — `MAIN_LINKED_STACK.cpp`. Проект особенно проверять с AddressSanitizer и UndefinedBehaviorSanitizer, если они доступны локально.

### Прикладной завершающий этап проекта 3: постфиксная запись

После реализации стека пользователь пишет **внешнюю функцию**, не метод класса, в файле `PostfixEvaluator.h` (при необходимости допустимо `.cpp` с добавлением в команду сборки):

```cpp
double evaluate_postfix(const std::string& expression);
```

Это тренировка задачи № 3 варианта «Стек» из университетской ЛР № 1. Не подменяй алгоритм готовым `std::stack` или контейнером STL; **использовать собственный `LinkedStack<double>`**.

Контракт: вход — токены, разделённые пробельными символами; числа могут быть целыми, дробными и со знаком (например, `-3`), операции `+`, `-`, `*`, `/` являются отдельными токенами. Каждая бинарная операция использует два верхних операнда в правильном порядке. После обработки корректного выражения в стеке ровно одно значение. Недостаток операндов, лишние операнды, неизвестный токен, пустое выражение и деление на ноль — `std::invalid_argument`. Примеры: `3 4 +` → 7; `5 1 2 + 4 * + 3 -` → 14.

Проверочный файл `MAIN_POSTFIX.cpp` должен запускаться **отдельно**, чтобы незавершённый алгоритм не блокировал тесты самого стека. Это последняя стадия третьего проекта, а не новая разрозненная задача.

## RTTI — короткое самостоятельное закрепление

Это **не четвёртый большой проект**. Сохрани масштаб примерно 20–30 минут.

В `RttiLab.h` ученик реализует:

- Полиморфную базу `Shape` с виртуальным деструктором и виртуальным `double area() const`.
- `Rectangle(double width, double height)` и `Circle(double radius)` с положительными/нулевыми геометрическими размерами. Отрицательные параметры — `std::invalid_argument`.
- `bool is_rectangle(const Shape&)` с проверяемым преобразованием.
- `const Rectangle& require_rectangle(const Shape&)` с приведением ссылки и возможным `std::bad_cast`.
- `bool is_exact_circle(const Shape&)` через `typeid` на полиморфном объекте.

Геометрические площади должны быть обычными математическими площадями: прямоугольник `width * height`, круг `π * r²`; значение π достаточно задавать как `3.14159265358979323846`.

Не использовать невалидные разыменования и не требовать запуска кода с неопределённым поведением. `const_cast` и `reinterpret_cast` изучаются в теории; они не требуются для решения этой задачи.

Локальная проверка — `MAIN_RTTI.cpp`.
